Session log — one long working conversation

Chasing a single flow to full speed

A log of one continuous session spent understanding this glorytun fork, then diagnosing and closing the gap between what a single TCP connection gets through a two-ISP bonded tunnel and what several connections get together — from first read of the codebase through a shipped, empirically-tested fix and a mid-flight redesign prompted by a real long-haul VPS.

The shape of the session, if you only read one thing
What was actually wrongNothing was broken — iperf3 -P1 measuring far below -P8 is TCP correctly reacting to real packet reordering caused by per-packet (not per-flow) multipath scheduling.
What got builtA resequencing buffer in mud.c (reorderwindow) that holds decrypted packets just long enough to restore send order before handing them to the TUN device — reusing data the transport already had, no wire-protocol change.
What almost shipped wrongThe first version applied one flat delay to every packet. A live test against a real ~200ms-RTT VPS showed that flat delay actively making things worse — fixed by making the hold adaptive per physical path, an idea that came from the user mid-session.
What else moved the needleBBR congestion control, applied on the real TCP endpoints (not the tunnel routers) — often the single biggest lever, separate from anything glorytun does.
What stayed a hard limitOne TCP connection has one congestion window and one RTT. Nothing here — or in any multipath tunnel — makes -P1 literally equal -P8; the honest target is closing the gap, not erasing it.

§Overview

The starting request was broad: read the whole codebase and understand it. That turned into a long-running investigation once real benchmark numbers came back showing a single-connection iperf3 test topping out around 70-90 Mbps over a tunnel that eight parallel connections could push past 500 Mbps combined. Everything that follows is the process of figuring out why, what could close that gap, building the part of the fix that lived inside glorytun itself, and the two rounds of real-world testing — one local, one against a VPS several hundred kilometers away — that each caught something the other couldn't have.

§Reading the codebase first

Every source file was read in full before any conclusions: mud/mud.c (the transport — key exchange, AEAD, multipath scheduling, worker threads), src/bind.c and the rest of the CLI, argz/, and the existing docs. Two things stood out immediately:

Docs described a design that was gone

docs/architecture.md and docs/cli-reference.md both still described an MTU discovery mechanism — binary search, mtumin/mtumax — that had been fully removed from the code. The actual behavior: one fixed, operator-set wire size per path, advertised to the peer, no probing at all. Both docs were rewritten to match.

The multipath scheduler is per packet

mud_select_path() picks a destination for every individual packet — a weighted-random draw across whatever paths are currently running, using the packet's own encrypted tail bytes as a free, uncoordinated source of randomness. This one fact turned out to explain almost everything that came later.

§Why -P1 never matched -P8

Because scheduling is per packet, a single TCP flow's packets are already being scattered across every bonded path — connections or not. On a link where the two ISPs have different round-trip times, that scattering means packets routinely arrive at the far end out of the order they were sent: a packet that took the fast path overtakes one sent slightly earlier on the slow path. TCP has no way to tell that apart from real loss — it sees a gap in sequence numbers, fires duplicate ACKs, and throttles the connection via fast retransmit, even though nothing was actually dropped.

Why several flows don't have the same problem Every flow in an -P8 test eats the identical reordering penalty individually — but running eight of them in parallel means their sum still saturates the link even while each one, alone, is throttled the same way a lone -P1 flow is. The aggregate number was never proof that reordering wasn't happening; it was proof that parallelism papers over it.

§Building the resequencing buffer

Option A landed inside mud.c: a small buffer on the receive side of mud_worker_loop() that holds a decrypted packet briefly, then releases it in send order instead of arrival order. Full detail — locking, wire-format reasoning, every iteration — lives in glorytun-notes.html's Packet resequencing section; the shape of it here:

No wire-protocol change

The final design runs entirely on RTT this side already measures locally — no new field, no both-ends-must-upgrade requirement, safe to deploy on one end at a time like everything else in this fork.

Empirically tested, not just written

WSL2, two network namespaces standing in for router and VPS, two veth pairs shaped with tc netem to real asymmetric RTTs, 16 real sub-flows — the same shape as the actual deployment, not a toy.

A bug the test caught, not the reasoning

The first mud_reorder_flush() only sorted the first 32 ready packets it found — correct within a batch, silently wrong once more than one batch was ready at once. The first live run showed retransmits going up with the feature on. Fixed by sorting the complete ready set before releasing anything.

Local WSL result, ~8ms / ~34ms RTT paths Baseline (off): 94.8 Mbps, 1146 retransmits  →  reorderwindow 25ms: 81.1 Mbps, 137 retransmits (88% fewer)

§First real-hardware round

Moving off the simulated environment onto the user's actual OpenWRT router and VPS surfaced a sequence of smaller, very real mixups — the kind that only show up once real infrastructure and real habits are involved.

Wrong side, wrong direction

Resequencing only ever helps the receiving end of a transfer. The first real test enabled it on the sender's own daemon — silently doing nothing for that direction. Caught from the topology (which host was the iperf3 client), not from the numbers.

"Is connections N round-robin?"

No — weighted-random, seeded from each packet's own ciphertext bytes. Needs no shared counter across worker threads, which plain round-robin would.

What's actually parallel

Every worker thread runs the entire pipeline — TUN I/O, crypto, path selection, socket I/O — not just encryption. Only tunnel-wide housekeeping (mud_update(), the control socket, netlink) stays on one thread, because it's cheap and infrequent, not because it was missed.

Why BBR outscored connections N

A single flow was already crossing both ISPs even with one sub-flow each — connections N never touches that. BBR and the resequencing buffer both attack the actual bottleneck directly; connections N was solving a different problem (ISP-side per-flow shaping) the user didn't clearly have.

§Getting congestion control right

Congestion control is strictly end-to-end — it only runs on the machine that actually opened the TCP socket. A router or tunnel gateway forwarding traffic in between never touches it, no matter how many hops or tunnels the packets cross. This became its own small investigation once it turned out the iperf3 server sometimes lived on a LAN device behind OpenWRT, not on OpenWRT itself — meaning BBR had to go on the real endpoint, not the router.

enabling BBR on OpenWRT (needs the kernel module first)
root@router:~# opkg update && opkg install kmod-tcp-bbr
root@router:~# modprobe tcp_bbr
root@router:~# sysctl -w net.ipv4.tcp_congestion_control=bbr
# persist across reboot:
root@router:~# echo tcp_bbr >> /etc/modules.d/30-tcp-bbr
root@router:~# echo "net.ipv4.tcp_congestion_control=bbr" >> /etc/sysctl.conf

Confirming it's actually active on a live connection (the sysctl only affects new sockets) — the bbr:(bw:...,mrtt:...,pacing_gain:...) block is the unambiguous tell:

ss -ti, mid-transfer, on whichever side is sending
ESTAB 0 0 10.77.0.1:53012 10.77.0.2:5201
	 bbr wscale:7,7 rto:204 rtt:2.921/1.5 ... pacing_rate 12.3Mbps delivery_rate 10.1Mbps
	 bbr:(bw:83.2Mbps,mrtt:2.899,pacing_gain:2.77295,cwnd_gain:2.77295)

§The long-haul regression, and the fix

Testing against a VPS several hundred kilometers away (~154ms and ~210ms RTT on the two paths — a real ~28ms one-way skew, nothing like the local WSL test's 8-34ms) exposed a second, more serious problem in the original design: a flat delay applied identically to every packet, including ones on the already-slow path with nothing to wait for. At low RTT that flat tax was negligible; at 150ms+ it was a real, proportionally significant addition to every round trip.

The regression, caught live reorderwindow 50ms (flat): 35.5 Mbps, 3074 retransmits — worse than doing nothing at all (baseline: 406 retransmits).

The fix came from a question the user asked directly: why hold packets on the slow path at all — only the fast one? That reframed the whole mechanism. mud_path.reorder_hold is now recomputed every mud_update() tick from each path's real measured RTT relative to the tunnel's current slowest path — the slowest path gets zero hold and skips the buffer entirely; only genuinely faster paths pay a delay, proportional to their real speed advantage. reorderwindow stopped being the delay itself and became a safety ceiling on an automatic, per-path value.

Same ~154/210ms RTT paths, after the redesign Baseline (off), 3 runs: 23-32 Mbps  →  adaptive reorderwindow 60ms, 2 runs: 33-39 Mbps — no longer a regression, trending toward a real improvement.

Single-flow TCP at this RTT stayed genuinely noisy run to run even at the identical setting in a simulated network — the direction of the result is the finding here, not the exact percentage. Real hardware, with no virtualization noise floor underneath it, should read cleaner.

§Code → build → test

  1. 01Code — done. Three files hold the whole feature: mud/mud.h, mud/mud.c, src/set.c.
  2. 02Build — same process as before on both machines, just newer source; OpenWRT through its existing SDK/feed pipeline, the VPS through the plain Makefile/meson build.
  3. 03Restart both daemons — not a live-reloadable change; the reorder buffer is allocated in mud_create().
  4. 04Set reorderwindow on both sides — it no longer needs to be precise (it's a ceiling now), but it does need setting explicitly on each end, since it never propagates automatically.
  5. 05Compare against a fresh baseline — restart with the feature off, measure, then re-enable and measure again. Watch retransmits as the more direct signal, not raw throughput alone.
