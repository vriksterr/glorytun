Reference — multipath encrypted tunnel

glorytun

A userspace VPN that opens a Linux TUN device on each end and carries traffic over one or more encrypted UDP paths — able to run several physical links (say, two PPPoE WANs) at once, live-tracking each one's health and shifting load as conditions change, and able to split a single link into several parallel UDP sub-flows to bond bandwidth on a long/high-RTT connection. These notes cover how it's built, what every command does, what its output looks like, and everything changed in this fork, session by session.

§Overview

Each side runs glorytun bind, which creates a TUN interface, opens a UDP socket, and begins exchanging encrypted packets — either AEGIS-256 with AES-NI/ARMv8-crypto hardware acceleration when available, or ChaCha20-Poly1305 as a software fallback. A path is one local/remote address pair, or on Linux, one physical interface (via wwan0) whose address and index are re-resolved automatically if it changes. Multiple paths can carry the same tunnel at once; each is tracked independently for round-trip time and packet loss, and traffic favors whichever paths are healthiest. A single path can also be split into several independent UDP sub-flows (connections N) — see UDP sub-flow bonding.

Everything else — show, set, path — talks to the running bind process over a local control socket, not the network.

§Architecture

One packet's round trip through the stack, on the sending side:

TUN deviceYour OS hands glorytun a plaintext IP packet
→
Path selectPick the healthiest path tied for best preference
→
EncryptAEGIS-256 or ChaCha20-Poly1305, on the worker pool
→
UDP socketsendmsg() onto that path's interface/address

A parallel channel of small "beat" messages (every 100ms by default, backing off to 25s once a path goes quiet) rides alongside real traffic to measure round-trip time, exchange real send/receive counters for loss accounting, and negotiate rate limits. Each beat also carries the sender's current fixed MTU purely as an informational value in the status output — nothing on the receiving side reacts to it or changes its own wire size because of it.

§Threading model

Only encryption/decryption is spread across cores. Everything else — socket I/O, path bookkeeping, rate and loss accounting — runs on a single thread by design.

Main thread

Runs the event loop: TUN read/write, UDP send/recv, path state machine, MTU probing, loss tracking. Also joins the crypto pool as a peer worker during batches — never idle while the pool works.

Worker pool

min(cores − 1, 8) threads, spawned once at startup. Asleep on a condition variable until a batch of packets needs encrypting or decrypting, then all wake, pull jobs from a shared counter, and sleep again.

Single-core fallback

Zero threads spawned. The main thread does every job inline — same code path, no pool overhead paid for machinery that has nowhere to run in parallel.

Total participating threads on an n-core box is exactly n (capped at 9) — n−1 spawned workers plus the main thread, never n+1, which would oversubscribe the CPU for no benefit. See bench multicore below for a way to actually measure what this design costs in practice.

§Path health, rewritten this session

Every path reports RTT and two loss figures per direction. All of it is derived from real packet counters — never a self-reported number taken on trust from the other end.

  • RTT — one number, not directional. Round-trip time of the beat-message exchange.
  • TX-LOSS — of what this side sent, how much the peer confirms receiving. Computed locally from the peer's real receive counters, not trusted blindly.
  • RX-LOSS — of what the peer sent, how much this side actually received. Also computed locally now — previously just copied the peer's own self-reported byte.

Both loss figures come in two flavors: a stable value (60-second rolling window, drives the degraded/lossy decision) and a live value (fresh every ~1 second, shown on the status page). Neither one is fabricated from too little evidence — while a path has carried no real traffic in the last second, both values freeze at their last honest reading instead of coin-flipping between 0% and 100% off a single stray heartbeat.

glorytun path's STATUS column reads one of these, checked top-to-bottom — the first match wins:

§Fixed MTU — no discovery, and why it used to break

The old design found each path's usable packet size once, on convergence, by a binary search: probe near the top of a range, narrow based on whether the peer confirmed it, repeat. It never worked reliably — convergence routinely stalled, so the path effectively never left probing. Worse, the mechanism could look "settled" without being correct: every beat interval each side re-advertised its own last-confirmed size, and the peer mirrored it back into its own belief, so two peers could sit there mutually re-confirming a stale number forever, neither one ever re-testing it against the current real path.

Separately, mud_send_path() incremented its sent-packet counters unconditionally, without checking whether sendmsg() actually succeeded. Combine the two: once the real path MTU shrank — a PPPoE renegotiation, a route change, a new hop mid-session — glorytun kept sending at the old, now-oversized size; the local kernel might reject it outright (EMSGSIZE), or a middlebox further out might silently swallow it (a PMTUD black hole, no local error at all). Either way TX-LOSS climbed because the peer never saw those packets — but the tiny beat/tracking messages stayed far under any realistic MTU, so they kept succeeding, keeping STATUS at running throughout. Control channel healthy, data channel silently dead.

The fix: remove discovery entirely. Rather than patch a binary search that had never once reliably converged, every path now uses a single fixed wire size you set explicitly, or a safe built-in default if you don't. No probing, no negotiation, no state that can go stale — mud_mtu_apply() is the only place the value is ever decided, and it runs once whenever a path's config changes.

Accounting fix (kept)

mud_send_path() only counts a send as sent when sendmsg() actually returned the full size. A failed send no longer inflates TX counters or consumes rate-limit budget — independent of the MTU redesign, still true today.

What was removed

mud_update_mtu(), mud_mtu_reprobe(), the min/max search range, the periodic 5-minute recheck, and the peer-mirroring belief exchange are gone from mud.c entirely — not disabled, deleted.

What replaced it

struct mud_path_conf.mtu — one uint64_t, 0 meaning "use the default." mud_mtu_apply() resolves it to path->mtu, clamped to MUD_MTU_HARD_MAX.

Set it per path with glorytun path up ... mtu N. Leave it unset and the path uses 1400 (MUD_MTU_DEFAULT in mud.c) — conservative enough to survive standard PPPoE overhead and typical VPN-in-VPN encapsulation without any manual tuning. Whatever value ends up in effect is advertised to the peer in every beat purely as an informational figure in the status output; the receiving side never reacts to it or changes its own size because of it.

The ceiling: MUD_MTU_HARD_MAX, now 65535. This used to be hard-locked at 1500 because the fixed packet buffers throughout mud.c were sized to exactly that, and a larger configured value would have overrun them — a real buffer overflow, not a policy choice. Rather than remove that check outright, the ceiling itself was raised to 65535 (UDP's own header length-field maximum) and every dependent buffer was resized to match — the heap-allocated batch job arrays in mud.c (mud_send_job/mud_recv_job.packet[], ×256 slots each) and, separately, src/bind.c's own tx_buf/rx_buf — the TUN-device read/write buffers, which had their own hardcoded 1500 literal, entirely disconnected from the library's constant. Fixing only mud.c and leaving that one alone would have just relocated the same overflow risk to a different file.

One caveat worth knowing, not a bug: over IPv4 (this deployment's case) a UDP payload can't actually reach the full 65535 — the datagram still has to fit inside an IPv4 packet, whose own total-length field tops out at 65535 and has to include a 20-byte IPv4 header. The practical IPv4 ceiling is 65507. A configured value between 65508 and 65535 passes every check here but will fail at sendmsg() on an IPv4 path — kept as 65535 deliberately (UDP's own textbook maximum) rather than 65507, so the small dead zone is a known, documented tradeoff rather than an oversight.

This raise costs real memory, paid once at startup regardless of what MTU you actually configure: the batch job arrays go from ~1.5MB combined to roughly ~66MB (heap in mud.c plus static/BSS in bind.c), since 256 slots are now sized for a 65535-byte packet each instead of 1500. Trivial for a VPS, worth confirming headroom on a constrained router.

setting a fixed MTU
root@joy:~# glorytun path up dev gt0 to addr 163.61.39.45 port 5000 mtu 1400
root@joy:~# glorytun path up via wwan0 mtu 70000
Option mtu must be a number less than or equal to 65535

A separate, real finding along the way: on a CPU-constrained box, the kernel's UDP receive buffer can also overflow under load (confirmed via nstat -az UdpRcvbufErrors UdpInErrors showing a live, climbing count) and produces the same symptom — elevated RX-LOSS with no code bug involved. A SO_RCVBUF increase was tried and worked, then was reverted at request to isolate the MTU work above on its own — worth re-considering later if buffer drops show up again independently.

§UDP sub-flow bonding — connections N

Multipath already meant "two different physical WAN links carrying one tunnel" — each its own path, independently tracked, load-balanced by mud_select_path(). This applies the same idea within one physical link: split a single path into several independent UDP sub-flows (distinct local source ports, same interface) so a link with a long round-trip time isn't capped at whatever one flow's own bandwidth-delay product allows — the same reason iperf3 -P4 outruns a single stream on a high-RTT connection, applied one layer below where a plain single TCP stream through the tunnel can see it.

The fit turned out unusually clean. mud_select_path() already sprays outgoing packets across every MUD_RUNNING path, weighted by each one's live measured rate, with no idea which physical interface a path belongs to — nothing about it needed to change to also spray across sub-flows of one interface. Every path's rate/loss/RTT tracking was already fully independent per struct mud_path. And because a path's identity on receive already keyed on remote port as well as address, a peer sending from several distinct source ports was already, incidentally, causing the far side to auto-create one passive path per port — this feature just makes that intentional instead of a side effect nobody was relying on.

What's new

A struct mud instance now owns a small pool of local UDP sockets instead of exactly one — grown on demand, realloc()'d the same way mud->paths already is. struct mud_path_conf.sock picks which pool socket a path uses, and joins path-identity matching everywhere local_ifindex/remote already did.

What didn't need to change

The AIMD rate controller, loss tracking, RTT, the crypto worker pool, and key exchange are all untouched — none of them have any concept of sockets, only of struct mud_path. mud_select_path() and the beat-cadence logic did end up touched, but only after real testing — see below.

What the peer needs

Nothing. The passive side auto-discovers one path per distinct source port it observes, exactly like it already did. No upgrade, no config — and its own reverse-direction sends load-balance across those auto-discovered paths automatically too, since a passive path reaches MUD_RUNNING through the identical state machine an explicit path does.

glorytun path up ... connections 4
root@joy:~# glorytun path up via pppoe-ISP1_WAN connections 4 rate tx 10mbit rx 50mbit

connections requires via IFACE — rejected client-side for legacy addr-based paths, since only the interface-managed path table has anywhere durable to track and later shrink a sub-flow count across calls. Default is 1 (today's single-socket behavior, unchanged); 0/unset leaves an existing path's count alone rather than resetting it. Shrinking a count later brings the excess sub-flows down the same way path down already does for a single path.

The ceiling isn't a design opinion. MUD_SOCK_MAX is 256 — the range of struct mud_path_conf.sock, a single unsigned char — not a number picked for sounding reasonable. The pool grows to whatever connections N actually asks for, the same way MUD_PATH_MAX already grows mud->paths on demand.

One real tradeoff, deliberately not fixed here: bind's event loop still uses select(2), which silently misbehaves once a tracked file descriptor's value reaches FD_SETSIZE (1024 on Linux). A handful to a few dozen sub-flows is fine on any normal process; requesting hundreds is where this would start to matter, and would call for switching to poll()/epoll() — out of scope here since it wasn't needed at the sizes this was actually built and asked for.

Two problems found working through what this implies in practice

1. Sub-flows were competing, not sharing. mud_select_path() weights selection by each path's tx.rate — correct for bonding two genuinely different-capacity physical links, wrong for sub-flows of one link, which have no real capacity difference from each other. Left alone, that's a rich-get-richer trap: whichever sub-flow(s) pull ahead early get selected more (selection weight is measured rate), which keeps their rate estimate growing while idle siblings never get real traffic to prove themselves against — risking most of the aggregate bandwidth quietly collapsing onto 1-2 sub-flows instead of spreading across all N.

Fixed with a new struct mud_path.select_weight, recomputed every mud_update() tick by a new mud_path_same_group() helper: every MUD_RUNNING path sharing one physical link (same interface, or local address for legacy/passive paths — and same remote address, deliberately not remote port, since sub-flows vary by local port on the active side but by remote port on the passive side, which never opens extra sockets) gets weighted as its group's average tx.rate instead of its own. mud_select_path() now reads select_weight, splitting packets evenly within a group while still favoring whichever physical link has more real aggregate capacity between groups. tx.rate itself is untouched — still each sub-flow's genuine measured throughput for display and its own AIMD growth.

2. Idle-looking sub-flows were going stale for up to 25 seconds. mud_path_track() backs a healthy path's beat cadence off from ~100ms to the global 25s keepalive once it's seen no traffic in the last second — sensible for a truly idle physical link, wrong for a sub-flow: with N of them splitting traffic, any individual one can look idle for a full second purely by chance while the link overall stays busy. Once backed off, its RTT/loss/rate only refresh when a beat reply is processed — so a `path watch` view that queries fresh every second was still showing genuinely stale per-sub-flow numbers underneath, and the sub-flow's tx.rate stopped being reassessed too, compounding problem 1.

Fixed by having mud_path_track() skip the idle backoff entirely whenever mud->sock_count > 1 — the simpler of two options weighed, at the cost of also keeping a lone non-bonded path's beat at full cadence just because some other path on the same daemon happens to use sub-flows. The overhead (a handful of small beats per sub-flow per 100ms) is trivial on any link worth bonding in the first place.

Seeing whether a sub-flow is actually carrying anything

Neither tx.rate nor the fixes above answer "is this specific sub-flow being used right now" — tx.rate is glorytun's own AIMD-allowed budget, not a live usage meter; an idle sub-flow can sit at a healthy tx.rate long after it stopped carrying anything. glorytun path now computes a real observed rate entirely client-side instead: each refresh diffs this call's cumulative byte counters against the previous call's, over the actual wall-clock time elapsed, with no daemon or protocol change involved. New tx/rx fields on every sub-flow line make an unused one immediately obvious:

glorytun path watch — one idle sub-flow

§Packet resequencing — reorderwindow

mud_select_path() schedules per packet, weighted by measured capacity — not per flow. Every packet of a single TCP connection can land on a different physical path depending on which one the weighted walk picks that moment, and since paths differ in RTT, those packets routinely arrive out of order at the far end. TCP reads that as loss — duplicate ACKs, fast retransmit — and throttles itself, even though nothing was actually dropped. This is the reason one iperf3 stream measures far below what several parallel streams add up to over the same bonded link: each stream individually eats the same reordering penalty, but running several in parallel lets their sum still saturate the link even while each one is throttled.

The fix

New mud_conf.reorder_window, off (0) by default. When set, mud_worker_loop()'s receive side briefly buffers decrypted data packets — tunnel-wide, across every path, since the reordering happens between paths — and releases them to the TUN device in send order instead of arrival order.

Adaptive per path, not one flat delay

New mud_path.reorder_hold, recomputed every mud_update() tick from each path's real measured RTT: how much longer, relative to the tunnel's current slowest RUNNING path, a packet on this specific path needs to wait. The slowest path itself gets 0 and skips the buffer entirely — nothing can be behind it. reorder_window still caps it, but no longer is it. A second-round fix, not the original design — see below.

Worker-loop only

Only mud_worker_loop()'s RX path is touched. The single-packet mud_recv()/mud_send() API — used directly by mud/test.c, bypassing worker threads entirely — is untouched by design, exactly as its own doc comment already promised.

Each buffered packet gets a deadline fixed at the moment it's buffered: local arrival time plus that packet's own path's reorder_hold (capped by reorder_window). mud_reorder_flush() simply releases everything whose deadline has passed, sorted by deadline. No wire-protocol change was needed even for this: the whole scheme runs on RTT this side already measures locally (the same beat-message RTT glorytun path already shows) and never touches the peer's clock at all — a stronger version of the original design's promise, which still read the peer's own send-timestamp field. The buffer never blocks or drops a packet to make room: one that doesn't fit, or whose own path's hold caps to zero, is simply delivered immediately — exactly like every packet is with the feature off. Correctness never depends on this buffer; only the reordering benefit does.

Two mutexes, doing different jobs. lock guards the buffer's own contents — plain memory access only, never held across a syscall, same discipline state_lock already follows elsewhere in mud.c. flush_lock is new territory for this file: it serializes the entire deliver-to-TUN phase across worker threads, not just the syscalls, because strict ordering requires that only one thread's batch of releases is ever in flight at a time — two threads flushing concurrently could otherwise interleave their own correctly-sorted batches with each other and reintroduce the exact reordering the buffer exists to remove.

Picking a ceiling, not a delay

Since reorder_hold is computed per path automatically now, reorder_window is a ceiling, not the delay itself — the actual hold applied to any given packet is min(that path's computed reorder_hold, reorder_window). Set it too low and you clip the real computed skew back down to a flat delay again, reintroducing the exact problem the per-path design fixed; set it generously above the real skew and it costs nothing, since the system never holds a packet longer than its own path's real computed skew actually calls for. The math below is still useful for sizing that ceiling sensibly (and for building intuition for what the system is doing automatically), just no longer for picking an exact number to apply to everything. glorytun path gives you RTT — round-trip, there and back — but the number that matters here is the one-way gap between your two paths, which is roughly half the RTT gap between them:

the formula
one-way skew ≈ (slower path's RTT − faster path's RTT) / 2

Read the two RTTs straight off glorytun path, one per physical via group — every sub-flow within one group rides the same physical link, so they'll all read close to each other; there's no need to compare all of them individually, one representative value per ISP is enough:

  ├─ 1  running  ...  rtt 20.487  ...
(remaining sub-flows omitted — all close to 20ms)

Example A — similar ISPs

15ms and 18ms RTT. Skew = (18 − 15) / 2 = 1.5ms. Barely any gap to cover — a small window (5-10ms) is plenty, or reordering was never really your bottleneck here.

Example B — realistic dual-ISP

20ms and 45ms RTT. Skew = (45 − 20) / 2 = 12.5ms. Start around 20ms — a bit above the raw number.

Example C — fiber + 4G/satellite backup

10ms and 120ms RTT. Skew = (120 − 10) / 2 = 55ms. Start around 70-80ms — but that's real latency added to everything on the tunnel just to smooth one especially slow path, worth questioning whether that path belongs in the bond at all versus kept as pure backup.

Pad above the raw skew number when setting the ceiling — real links jitter, especially under the load that makes this matter most, and since the ceiling costs nothing when it isn't the binding constraint, there's little reason to shave it close. Watch Retr (retransmits) on a real transfer more than raw throughput to judge whether it's doing its job — it's the more direct signal of whether reordering-triggered false loss is actually being removed.

A bug that only real testing caught

The first implementation capped the readiness scan at 32 entries per pass — sort whatever's found, ship it, repeat. That sorts correctly within one batch of 32, but under real sustained throughput, well over 32 packets are routinely ready to release at once, scattered through the buffer in whatever order they happened to be inserted — not sent-time order. The scan would stop at the first 32 it found in array order, sort those correctly, and defer anything with a smaller sent_time that just hadn't been scanned yet to a later pass — releasing it after packets that were actually sent later. Sorted per batch, but not globally. This was caught, not reasoned around: the very first live test showed retransmits going up with the feature on (197 → 1412), the opposite of the point of building it. Fixed by scanning and sorting the complete ready set before releasing anything, then chunking only the data-copy/delivery step afterward for bounded stack usage — the sort establishes the order once, chunking never gets to disturb it.

Actually built and run this time

Unlike the sessions below, this one wasn't just written and left uncompiled (see the closing note on this page) — it was built and tested end to end in WSL2: two network namespaces standing in for the router and the VPS, joined by two veth pairs shaped with tc netem to roughly 8ms and 34ms RTT — deliberately asymmetric, matching a real dual-ISP setup — each capped at 300mbit, with connections 8 per path (16 real sub-flows), the same shape as a real deployment.

single-flow iperf3, fresh daemon restart per condition
baseline (reorderwindow off)      94.8 Mbps    1146 retransmits
reorderwindow 25ms                81.1 Mbps     137 retransmits   (88% fewer)

Throughput moved in both directions across repeated runs — WSL2/netem itself turned out noisy under 16 concurrent shaped UDP sub-flows (individual sub-flows intermittently showing real loss with the feature off, one transient iperf3 control-connection reset, neither reproducible on retry) — but the retransmit-count drop was large and consistent in every clean run. That's the more direct signal of whether this mechanism is doing its job at all, since it's what the feature specifically targets; the noisier throughput numbers are believed to reflect the simulated environment, not the code, and real hardware should read cleaner on both counts.

One real-world mixup worth recording: resequencing only ever helps the receiving side of a given transfer — the sender doesn't reorder anything, it only stripes packets out. Set on the wrong end (the sender's own daemon) it silently does nothing for that direction. First real-hardware test enabled it on the wrong side for exactly this reason before the mistake was caught from the topology, not the numbers.

A flat window doesn't survive contact with a real long-haul path

The local WSL2 test above ran at 8-34ms RTT. Testing against a real VPS several hundred km away (~154ms and ~210ms RTT on the two paths, a ~28ms real one-way skew) exposed something the local test never could: the original flat-window design applies the same delay to every packet, including ones on the already-slow path that have nothing to wait for. At low RTT that flat tax is negligible next to the real transit time; at 150-200ms+ RTT it's a real, proportionally significant addition to every round trip — and a reorderwindow approaching the housekeeping loop's own ~100ms poll cadence introduced a second problem on top: release timing became inconsistent (some packets flushed quickly on real traffic, others waiting a full poll cycle), and that inconsistency in delay is exactly the kind of thing that confuses TCP's own RTO estimate.

flat window, ~154/210ms RTT paths, single flow
baseline (off)                    32-41 Mbps    406-1596 retransmits (noisy)
flat reorderwindow 20ms           24.9 Mbps        46 retransmits   (throughput down)
flat reorderwindow 50ms           35.5 Mbps      3074 retransmits   (worse than baseline)

50ms made retransmits worse than doing nothing at all — the opposite of the point, and the second time this feature has been caught regressing by a live test rather than by reasoning about the code (see the batch-scan bug above). The fix wasn't a bigger or smaller flat number -- it was recognizing the flat delay itself was the wrong shape: mud_path.reorder_hold now makes the delay adaptive per path, computed from real measured RTT (see the redesign described above), so a packet on the already-slowest path pays nothing at all, and only genuinely faster paths pay a delay proportional to their real speed advantage.

adaptive per-path hold, same ~154/210ms RTT paths, 60ms ceiling
baseline (off), 3 runs             23-32 Mbps      406-1596 retransmits
adaptive reorderwindow 60ms, 2 runs 33-39 Mbps    1100-1165 retransmits

No longer a regression -- trending toward a real ~35% throughput improvement across repeated runs, though single-flow TCP at this RTT stays inherently noisy in a simulated network even run to run at the same setting, so treat the direction as the finding, not the exact percentage. The idea for the adaptive redesign -- "why hold packets on the slow path at all, only the fast one" -- came from the user, not from re-reasoning about the code; the flat-window regression on its own hadn't obviously pointed at that particular fix.

glorytun set ... reorderwindow 20ms
root@joy:~# glorytun set dev gt0 reorderwindow 20ms
set dev gt0 kxtimeout 1h timetolerance 10m keepalive 25s reorderwindow 20ms

Same convention as keepalive/timetolerance/kxtimeout: 0 means "leave unchanged," not "disable" — once set, it can only be raised to a new value through this command, never reset back to 0 without restarting the daemon.

§Commands

Every subcommand, what it does, and what typing it actually shows you.
glorytun keygen

Generates a new secret key and writes it to stdout (or a file). Both ends of a tunnel share the same key.

keygen > gt.key
root@joy:~# glorytun keygen > gt.key
root@joy:~# cat gt.key
f3a1c9...e207b4  (64 hex chars, 32-byte key)
glorytun bind [dev NAME] [addr LOCAL_IP [PORT]] keyfile FILE [persist] [chacha] [qlen N] qlen is new

Starts the tunnel: creates/attaches the TUN device (on Linux, attaches to a pre-existing device of that name if one exists), opens the UDP socket, and runs the event loop until stopped. Runs in the foreground.

persist keeps the Linux TUN device alive when the process exits — useful with via-bound paths so netifd doesn't flap the interface across a crash/respawn. chacha forces the ChaCha20-Poly1305 fallback instead of negotiating AEGIS-256. qlen sets the TUN device's tx queue length (txqueuelen) once at startup — Linux defaults TUN/TAP interfaces to 500 (vs. 1000 for a typical Ethernet interface); raise it if real bulk traffic through the tunnel could burst past that. Unlike mtu on path up, this is a one-time value applied once when the interface is created, not something that needs to keep tracking path config afterward.

server
root@joy:~# glorytun bind dev gt0 keyfile /etc/glorytun/gt.key from addr 0.0.0.0 port 5000 qlen 1000
(runs in the foreground until Ctrl+C / SIGTERM)

RX-LOSS no longer trusted from the peer. Previously copied the peer's self-reported loss byte directly; now derived locally from the peer's real tx counters (already sent in every message) against this side's own real rx counters — same standard TX-LOSS already used.

Fixed the "running but dead" bug, then removed the mechanism that caused it. mud_send_path() now only counts a send as successful when sendmsg() actually returned the full size, instead of unconditionally — kept. mud/mud.h
mud/mud.c

Two problems found from working through what the design implies in practice, both requested explicitly after real testing, not speculative hardening.

Sub-flows were being selected by measured rate, not evenly. mud_select_path() weights by tx.rate — correct for bonding two different-capacity physical links, wrong for sub-flows of one link, which have no real capacity difference from each other. Left alone: a rich-get-richer trap, since whichever sub-flow(s) pull ahead early get selected more (selection weight is measured rate), keeping their rate estimate growing while idle siblings never get real traffic to prove themselves against. New struct mud_path.select_weight (mud.h), recomputed every mud_update() tick: a new mud_path_same_group() helper (next to mud_cmp_addr()/mud_cmp_port()) identifies which MUD_RUNNING paths share one physical link — same local_ifindex (or local address for legacy/passive paths) and same remote address, deliberately excluding remote port, since sub-flows vary by local port on the active side but by remote port on the passive side, which never opens extra sockets. Every path's select_weight becomes its group's average tx.rate, so mud_select_path()'s walk (now reading select_weight instead of tx.rate directly) splits packets evenly within a group while still weighting proportionally between distinct physical links. mud->rate is recomputed from the sum of select_weight rather than reused from the original tx.rate sum, so integer-division rounding inside each group's average can't leave the two inconsistent — mud_select_path()'s cursor is scaled against mud->rate, and any drift there risks the walk running past the last path without finding a match. tx.rate itself is untouched, still each sub-flow's genuine measured throughput for display and its own AIMD growth/decay.

Idle-looking sub-flows were going stale for up to 25 seconds. mud_path_track() backs a MUD_RUNNING path's beat cadence off from ~100ms to the global 25s keepalive once it's seen no traffic in the last second — sensible for a genuinely idle physical link, wrong for a sub-flow: with N of them splitting traffic, any individual one can look idle for a full second purely by chance while the link overall stays busy. Once backed off, its RTT/loss/rate only refresh when a beat reply is processed, and its tx.rate stops being reassessed too — compounding the selection problem above. Fixed with the simpler of two options weighed: mud_path_track() now skips the idle backoff entirely whenever mud->sock_count > 1, rather than only for paths actually grouped into a connections > 1 set — coarser (also keeps a lone non-bonded path's beat at full cadence just because some other path on the same daemon uses sub-flows), but correspondingly simpler, and the overhead is trivial on any link worth bonding sub-flows over.

src/path.c

New tx/rx fields on every sub-flow line (default and stat views, not rtt) show a real observed rate, answering a question neither existing field could: is this specific sub-flow actually carrying anything right now. tx.rate/rx.rate are glorytun's own AIMD-allowed budget, not a usage meter — an idle sub-flow can sit at a healthy tx.rate long after it stopped moving data.

Computed entirely client-side rather than adding daemon/protocol tracking: new gt_path_track_rate() keeps a static, per-(ifname, remote, sock) sample table and diffs each refresh's cumulative tx.bytes/rx.bytes against the previous refresh's, over the actual wall-clock time elapsed (clock_gettime(CLOCK_MONOTONIC) via a new gt_path_now_ns(), mirroring the existing pattern in src/bench.c). Formatted through the already-existing gt_torate() helper for consistency with how configured rate limits are already shown elsewhere in this file. Needs two samples a second apart, so it only produces a number under watch — a one-shot glorytun path query has nothing prior to diff against and shows -.

mud/mud.h

New mud_conf.reorder_window — 0 (default) disables it, matching every other duration field on struct mud_conf.

mud/mud.c

New fixed-size, always-allocated struct mud_reorder (MUD_REORDER_MAX slots × MUD_REORDER_SLOT_SIZE 2048 bytes) embedded in struct mud — same no-realloc() rationale mud->paths/mud->sock already follow post-rewrite: a pointer a worker thread holds can't be invalidated by another thread resizing it. Costs nothing when reorder_window is 0 beyond the one-time allocation. Started at 512 slots (~10ms of headroom at 600Mbit); raised to 4096 (~8.5MB) once real testing against a ~200ms-RTT path showed it silently undersized — see below.

New mud_reorder_insert() and mud_reorder_flush(), called from mud_worker_loop()'s RX delivery step and its poll-timeout branch. A packet mud_reorder_insert() can't buffer (full, oversized, or its own path's hold caps to zero) still gets delivered immediately by the caller instead of dropped — the buffer is strictly additive, never a new failure mode.

Two new mutexes on struct mud (reorder.lock, reorder.flush_lock), initialized/destroyed alongside the existing state_lock/keyx_lock in mud_create()/mud_delete(). mud_set() threads reorder_window through the same if (conf->x) c.x = conf->x pattern every other field already uses.

Went through three iterations, not one — (1) the first mud_reorder_flush() capped its readiness scan at MUD_REORDER_FLUSH_BATCH (32) entries per pass, sorting correctly within a batch but not across batches once more than one batch's worth was ready at once, caught live when retransmits went up instead of down; fixed by scanning and sorting the complete ready set first, chunking only the delivery copy afterward. (2) The buffer itself was undersized for a real long-haul path (512 slots covers ~10ms at 600Mbit; a ~200ms-RTT path needs a 40-60ms window, i.e. thousands of slots) — raised MUD_REORDER_MAX to 4096. (3) Even with more capacity, one flat reorder_window applied identically to every packet turned out to measurably hurt single-flow throughput at that same real RTT (see Packet resequencing's "flat window doesn't survive contact with a real long-haul path"). Redesigned around a new mud_path.reorder_hold (mud.h) -- recomputed every mud_update() tick, same cadence as select_weight, from each RUNNING path's real rtt.val relative to the slowest RUNNING path -- so mud_reorder_insert() now takes a per-packet hold (capped by reorder_window) instead of comparing against a global watermark, and each slot stores a precomputed deadline instead of sent_time/local_time -- mud_reorder_flush() simplified to just releasing whatever's past its deadline, sorted by deadline. mud_recv_finish() gained a reorder_hold_out parameter so it can hand back the already-resolved path's hold value at zero extra cost (it already holds state_lock with path in hand at that point); mud_recv() passes NULL, unaffected. The wire-format sent_time field is no longer read for this at all -- the redesign runs entirely on RTT this side already measures locally.
