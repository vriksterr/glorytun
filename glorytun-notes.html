Reference — multipath encrypted tunnel

glorytun

A userspace VPN that opens a Linux TUN device on each end and carries traffic over one or more encrypted UDP paths — able to run several physical links (say, two PPPoE WANs) at once, live-tracking each one's health and shifting load as conditions change, and able to split a single link into several parallel UDP sub-flows to bond bandwidth on a long/high-RTT connection. These notes cover how it's built, what every command does, what its output looks like, and everything changed in this fork, session by session.

§Overview

Each side runs glorytun bind, which creates a TUN interface, opens a UDP socket, and begins exchanging encrypted packets — either AEGIS-256 with AES-NI/ARMv8-crypto hardware acceleration when available, or ChaCha20-Poly1305 as a software fallback. A path is one local/remote address pair, or on Linux, one physical interface (via wwan0) whose address and index are re-resolved automatically if it changes. Multiple paths can carry the same tunnel at once; each is tracked independently for round-trip time and packet loss, and traffic favors whichever paths are healthiest. A single path can also be split into several independent UDP sub-flows (connections N) — see UDP sub-flow bonding.

Everything else — show, set, path — talks to the running bind process over a local control socket, not the network.

§Architecture

One packet's round trip through the stack, on the sending side:

TUN deviceYour OS hands glorytun a plaintext IP packet
→

→
EncryptAEGIS-256 or ChaCha20-Poly1305, on the worker pool
→
UDP socketsendmsg() onto that path's interface/address

A parallel channel of small "beat" messages (every 100ms by default, backing off to 25s once a path goes quiet) rides alongside real traffic to measure round-trip time, exchange real send/receive counters for loss accounting, and negotiate rate limits. Each beat also carries the sender's current fixed MTU purely as an informational value in the status output — nothing on the receiving side reacts to it or changes its own wire size because of it.

§Threading model

Only encryption/decryption is spread across cores. Everything else — socket I/O, path bookkeeping, rate and loss accounting — runs on a single thread by design.

Main thread

Runs the event loop: TUN read/write, UDP send/recv, path state machine, MTU probing, loss tracking. Also joins the crypto pool as a peer worker during batches — never idle while the pool works.

Worker pool

min(cores − 1, 8) threads, spawned once at startup. Asleep on a condition variable until a batch of packets needs encrypting or decrypting, then all wake, pull jobs from a shared counter, and sleep again.

Single-core fallback

Zero threads spawned. The main thread does every job inline — same code path, no pool overhead paid for machinery that has nowhere to run in parallel.

Total participating threads on an n-core box is exactly n (capped at 9) — n−1 spawned workers plus the main thread, never n+1, which would oversubscribe the CPU for no benefit. See bench multicore below for a way to actually measure what this design costs in practice.

Superseded by a later session: each worker now runs the entire per-packet pipeline itself (TUN read, encrypt/decrypt, path lookup, send) instead of only crypto — there's no separate main-thread-does-everything-else design anymore, and the cap moved from 8 to 32, with the count now operator-settable. See Scaling for many-core hardware for the current model and why the raised default alone turned out to be a real performance regression. Later still: each worker also has its own TUN queue, and the process can be confined to chosen cores — see Core placement & interrupts. The always-present extra thread is now purely housekeeping (path tick, control socket, network events), not a packet worker.

§Path health, rewritten this session

Every path reports RTT and two loss figures per direction. All of it is derived from real packet counters — never a self-reported number taken on trust from the other end.

  • RTT — one number, not directional. Round-trip time of the beat-message exchange.
  • TX-LOSS — of what this side sent, how much the peer confirms receiving. Computed locally from the peer's real receive counters, not trusted blindly.
  • RX-LOSS — of what the peer sent, how much this side actually received. Also computed locally now — previously just copied the peer's own self-reported byte.

Both loss figures come in two flavors: a stable value (60-second rolling window, drives the degraded/lossy decision) and a live value (fresh every ~1 second, shown on the status page). Neither one is fabricated from too little evidence — while a path has carried no real traffic in the last second, both values freeze at their last honest reading instead of coin-flipping between 0% and 100% off a single stray heartbeat.

glorytun path's STATUS column reads one of these, checked top-to-bottom — the first match wins:

§Fixed MTU — no discovery, and why it used to break

The old design found each path's usable packet size once, on convergence, by a binary search: probe near the top of a range, narrow based on whether the peer confirmed it, repeat. It never worked reliably — convergence routinely stalled, so the path effectively never left probing. Worse, the mechanism could look "settled" without being correct: every beat interval each side re-advertised its own last-confirmed size, and the peer mirrored it back into its own belief, so two peers could sit there mutually re-confirming a stale number forever, neither one ever re-testing it against the current real path.

Separately, mud_send_path() incremented its sent-packet counters unconditionally, without checking whether sendmsg() actually succeeded. Combine the two: once the real path MTU shrank — a PPPoE renegotiation, a route change, a new hop mid-session — glorytun kept sending at the old, now-oversized size; the local kernel might reject it outright (EMSGSIZE), or a middlebox further out might silently swallow it (a PMTUD black hole, no local error at all). Either way TX-LOSS climbed because the peer never saw those packets — but the tiny beat/tracking messages stayed far under any realistic MTU, so they kept succeeding, keeping STATUS at running throughout. Control channel healthy, data channel silently dead.

The fix: remove discovery entirely. Rather than patch a binary search that had never once reliably converged, every path now uses a single fixed wire size you set explicitly, or a safe built-in default if you don't. No probing, no negotiation, no state that can go stale — mud_mtu_apply() is the only place the value is ever decided, and it runs once whenever a path's config changes.

Accounting fix (kept)

mud_send_path() only counts a send as sent when sendmsg() actually returned the full size. A failed send no longer inflates TX counters or consumes rate-limit budget — independent of the MTU redesign, still true today.

What was removed

mud_update_mtu(), mud_mtu_reprobe(), the min/max search range, the periodic 5-minute recheck, and the peer-mirroring belief exchange are gone from mud.c entirely — not disabled, deleted.

What replaced it

struct mud_path_conf.mtu — one uint64_t, 0 meaning "use the default." mud_mtu_apply() resolves it to path->mtu, clamped to MUD_MTU_HARD_MAX.

Set it per path with glorytun path up ... mtu N. Leave it unset and the path uses 1400 (MUD_MTU_DEFAULT in mud.c) — conservative enough to survive standard PPPoE overhead and typical VPN-in-VPN encapsulation without any manual tuning. Whatever value ends up in effect is advertised to the peer in every beat purely as an informational figure in the status output; the receiving side never reacts to it or changes its own size because of it.

The ceiling: MUD_MTU_HARD_MAX, now 65535. This used to be hard-locked at 1500 because the fixed packet buffers throughout mud.c were sized to exactly that, and a larger configured value would have overrun them — a real buffer overflow, not a policy choice. Rather than remove that check outright, the ceiling itself was raised to 65535 (UDP's own header length-field maximum) and every dependent buffer was resized to match — the heap-allocated batch job arrays in mud.c (mud_send_job/mud_recv_job.packet[], ×256 slots each) and, separately, src/bind.c's own tx_buf/rx_buf — the TUN-device read/write buffers, which had their own hardcoded 1500 literal, entirely disconnected from the library's constant. Fixing only mud.c and leaving that one alone would have just relocated the same overflow risk to a different file.

One caveat worth knowing, not a bug: over IPv4 (this deployment's case) a UDP payload can't actually reach the full 65535 — the datagram still has to fit inside an IPv4 packet, whose own total-length field tops out at 65535 and has to include a 20-byte IPv4 header. The practical IPv4 ceiling is 65507. A configured value between 65508 and 65535 passes every check here but will fail at sendmsg() on an IPv4 path — kept as 65535 deliberately (UDP's own textbook maximum) rather than 65507, so the small dead zone is a known, documented tradeoff rather than an oversight.

This raise costs real memory, paid once at startup regardless of what MTU you actually configure: the batch job arrays go from ~1.5MB combined to roughly ~66MB (heap in mud.c plus static/BSS in bind.c), since 256 slots are now sized for a 65535-byte packet each instead of 1500. Trivial for a VPS, worth confirming headroom on a constrained router.

setting a fixed MTU
root@joy:~# glorytun path up dev gt0 to addr 163.61.39.45 port 5000 mtu 1400
root@joy:~# glorytun path up via wwan0 mtu 70000
Option mtu must be a number less than or equal to 65535

A separate, real finding along the way: on a CPU-constrained box, the kernel's UDP receive buffer can also overflow under load (confirmed via nstat -az UdpRcvbufErrors UdpInErrors showing a live, climbing count) and produces the same symptom — elevated RX-LOSS with no code bug involved. A SO_RCVBUF increase was tried and worked, then was reverted at request to isolate the MTU work above on its own — worth re-considering later if buffer drops show up again independently.

§UDP sub-flow bonding — connections N

Multipath already meant "two different physical WAN links carrying one tunnel" — each its own path, independently tracked, load-balanced by mud_select_path(). This applies the same idea within one physical link: split a single path into several independent UDP sub-flows (distinct local source ports, same interface) so a link with a long round-trip time isn't capped at whatever one flow's own bandwidth-delay product allows — the same reason iperf3 -P4 outruns a single stream on a high-RTT connection, applied one layer below where a plain single TCP stream through the tunnel can see it.

The fit turned out unusually clean. mud_select_path() already sprays outgoing packets across every MUD_RUNNING path, weighted by each one's live measured rate, with no idea which physical interface a path belongs to — nothing about it needed to change to also spray across sub-flows of one interface. Every path's rate/loss/RTT tracking was already fully independent per struct mud_path. And because a path's identity on receive already keyed on remote port as well as address, a peer sending from several distinct source ports was already, incidentally, causing the far side to auto-create one passive path per port — this feature just makes that intentional instead of a side effect nobody was relying on.

What's new

A struct mud instance now owns a small pool of local UDP sockets instead of exactly one — grown on demand, realloc()'d the same way mud->paths already is. struct mud_path_conf.sock picks which pool socket a path uses, and joins path-identity matching everywhere local_ifindex/remote already did.

What didn't need to change

The AIMD rate controller, loss tracking, RTT, the crypto worker pool, and key exchange are all untouched — none of them have any concept of sockets, only of struct mud_path. mud_select_path() and the beat-cadence logic did end up touched, but only after real testing — see below.

What the peer needs

Nothing. The passive side auto-discovers one path per distinct source port it observes, exactly like it already did. No upgrade, no config — and its own reverse-direction sends load-balance across those auto-discovered paths automatically too, since a passive path reaches MUD_RUNNING through the identical state machine an explicit path does.

glorytun path up ... connections 4
root@joy:~# glorytun path up via pppoe-ISP1_WAN connections 4 rate tx 10mbit rx 50mbit

connections requires via IFACE — rejected client-side for legacy addr-based paths, since only the interface-managed path table has anywhere durable to track and later shrink a sub-flow count across calls. Default is 1 (today's single-socket behavior, unchanged); 0/unset leaves an existing path's count alone rather than resetting it. Shrinking a count later brings the excess sub-flows down the same way path down already does for a single path.

The ceiling isn't a design opinion. MUD_SOCK_MAX was originally 256 — the range of struct mud_path_conf.sock, a single unsigned char — not a number picked for sounding reasonable. The pool grows to whatever connections N actually asks for, the same way MUD_PATH_MAX already grows mud->paths on demand. Both ceilings, and the unsigned char field itself, were later raised — see Scaling for many-core hardware.

One real tradeoff, deliberately not fixed here: bind's event loop still uses select(2), which silently misbehaves once a tracked file descriptor's value reaches FD_SETSIZE (1024 on Linux). A handful to a few dozen sub-flows is fine on any normal process; requesting hundreds is where this would start to matter, and would call for switching to poll()/epoll() — out of scope here since it wasn't needed at the sizes this was actually built and asked for.

Two problems found working through what this implies in practice

1. Sub-flows were competing, not sharing. mud_select_path() weights selection by each path's tx.rate — correct for bonding two genuinely different-capacity physical links, wrong for sub-flows of one link, which have no real capacity difference from each other. Left alone, that's a rich-get-richer trap: whichever sub-flow(s) pull ahead early get selected more (selection weight is measured rate), which keeps their rate estimate growing while idle siblings never get real traffic to prove themselves against — risking most of the aggregate bandwidth quietly collapsing onto 1-2 sub-flows instead of spreading across all N.

Fixed with a new struct mud_path.select_weight, recomputed every mud_update() tick by a new mud_path_same_group() helper: every MUD_RUNNING path sharing one physical link (same interface, or local address for legacy/passive paths — and same remote address, deliberately not remote port, since sub-flows vary by local port on the active side but by remote port on the passive side, which never opens extra sockets) gets weighted as its group's average tx.rate instead of its own. mud_select_path() now reads select_weight, splitting packets evenly within a group while still favoring whichever physical link has more real aggregate capacity between groups. tx.rate itself is untouched — still each sub-flow's genuine measured throughput for display and its own AIMD growth.

2. Idle-looking sub-flows were going stale for up to 25 seconds. mud_path_track() backs a healthy path's beat cadence off from ~100ms to the global 25s keepalive once it's seen no traffic in the last second — sensible for a truly idle physical link, wrong for a sub-flow: with N of them splitting traffic, any individual one can look idle for a full second purely by chance while the link overall stays busy. Once backed off, its RTT/loss/rate only refresh when a beat reply is processed — so a `path watch` view that queries fresh every second was still showing genuinely stale per-sub-flow numbers underneath, and the sub-flow's tx.rate stopped being reassessed too, compounding problem 1.

Fixed by having mud_path_track() skip the idle backoff entirely whenever mud->sock_count > 1 — the simpler of two options weighed, at the cost of also keeping a lone non-bonded path's beat at full cadence just because some other path on the same daemon happens to use sub-flows. The overhead (a handful of small beats per sub-flow per 100ms) is trivial on any link worth bonding in the first place.

Seeing whether a sub-flow is actually carrying anything

Neither tx.rate nor the fixes above answer "is this specific sub-flow being used right now" — tx.rate is glorytun's own AIMD-allowed budget, not a live usage meter; an idle sub-flow can sit at a healthy tx.rate long after it stopped carrying anything. glorytun path now computes a real observed rate entirely client-side instead: each refresh diffs this call's cumulative byte counters against the previous call's, over the actual wall-clock time elapsed, with no daemon or protocol change involved. §Packet resequencing — reorderwindow

mud_select_path() schedules per packet, weighted by measured capacity — not per flow. Every packet of a single TCP connection can land on a different physical path depending on which one the weighted walk picks that moment, and since paths differ in RTT, those packets routinely arrive out of order at the far end. TCP reads that as loss — duplicate ACKs, fast retransmit — and throttles itself, even though nothing was actually dropped. This is the reason one iperf3 stream measures far below what several parallel streams add up to over the same bonded link: each stream individually eats the same reordering penalty, but running several in parallel lets their sum still saturate the link even while each one is throttled.

The fix

New mud_conf.reorder_window, off (0) by default. When set, mud_worker_loop()'s receive side briefly buffers decrypted data packets — tunnel-wide, across every path, since the reordering happens between paths — and releases them to the TUN device in send order instead of arrival order.

Adaptive per path, not one flat delay

New mud_path.reorder_hold, recomputed every mud_update() tick from each path's real measured RTT: how much longer, relative to the tunnel's current slowest RUNNING path, a packet on this specific path needs to wait. The slowest path itself gets 0 and skips the buffer entirely — nothing can be behind it — and so does any path within 0.5 ms of it (that is RTT noise, not a real difference). reorder_window still caps it, but no longer is it. A second-round fix, not the original design — see below.

Worker-loop only

Only mud_worker_loop()'s RX path is touched. The single-packet mud_recv()/mud_send() API — used directly by mud/test.c, bypassing worker threads entirely — is untouched by design, exactly as its own doc comment already promised.

Each buffered packet gets a deadline fixed at the moment it's buffered: local arrival time plus that packet's own path's reorder_hold (capped by reorder_window). mud_reorder_flush() simply releases everything whose deadline has passed, sorted by deadline; workers sleep in poll() only until the earliest pending deadline, so a release is never left waiting for unrelated traffic. No wire-protocol change was needed even for this: the whole scheme runs on RTT this side already measures locally (the same beat-message RTT glorytun path already shows) and never touches the peer's clock at all — a stronger version of the original design's promise, which still read the peer's own send-timestamp field. The buffer never blocks or drops a packet to make room: one that doesn't fit, or whose own path's hold caps to zero, is simply delivered immediately — exactly like every packet is with the feature off. Correctness never depends on this buffer; only the reordering benefit does.

Two mutexes, doing different jobs. lock guards the buffer's own contents — plain memory access only, never held across a syscall, same discipline state_lock already follows elsewhere in mud.c. flush_lock is new territory for this file: it serializes the entire deliver-to-TUN phase across worker threads, not just the syscalls, because strict ordering requires that only one thread's batch of releases is ever in flight at a time — two threads flushing concurrently could otherwise interleave their own correctly-sorted batches with each other and reintroduce the exact reordering the buffer exists to remove.

Picking a ceiling, not a delay

Since reorder_hold is computed per path automatically now, reorder_window is a ceiling, not the delay itself — the actual hold applied to any given packet is min(that path's computed reorder_hold, reorder_window). Set it too low and you clip the real computed skew back down to a flat delay again, reintroducing the exact problem the per-path design fixed; set it generously above the real skew and it costs nothing, since the system never holds a packet longer than its own path's real computed skew actually calls for. The math below is still useful for sizing that ceiling sensibly (and for building intuition for what the system is doing automatically), just no longer for picking an exact number to apply to everything. glorytun path gives you RTT — round-trip, there and back — but the number that matters here is the one-way gap between your two paths, which is roughly half the RTT gap between them:

the formula
one-way skew ≈ (slower path's RTT − faster path's RTT) / 2

Read the two RTTs straight off glorytun path, one per physical via group — every sub-flow within one group rides the same physical link, so they'll all read close to each other; there's no need to compare all of them individually, one representative value per ISP is enough:

Example A — similar ISPs

15ms and 18ms RTT. Skew = (18 − 15) / 2 = 1.5ms. Barely any gap to cover — a small window (5-10ms) is plenty, or reordering was never really your bottleneck here.

Example B — realistic dual-ISP

20ms and 45ms RTT. Skew = (45 − 20) / 2 = 12.5ms. Start around 20ms — a bit above the raw number.

Example C — fiber + 4G/satellite backup

10ms and 120ms RTT. Skew = (120 − 10) / 2 = 55ms. Start around 70-80ms — but that's real latency added to everything on the tunnel just to smooth one especially slow path, worth questioning whether that path belongs in the bond at all versus kept as pure backup.

Pad above the raw skew number when setting the ceiling — real links jitter, especially under the load that makes this matter most, and since the ceiling costs nothing when it isn't the binding constraint, there's little reason to shave it close. Watch Retr (retransmits) on a real transfer more than raw throughput to judge whether it's doing its job — it's the more direct signal of whether reordering-triggered false loss is actually being removed.

A bug that only real testing caught

The first implementation capped the readiness scan at 32 entries per pass — sort whatever's found, ship it, repeat. That sorts correctly within one batch of 32, but under real sustained throughput, well over 32 packets are routinely ready to release at once, scattered through the buffer in whatever order they happened to be inserted — not sent-time order. The scan would stop at the first 32 it found in array order, sort those correctly, and defer anything with a smaller sent_time that just hadn't been scanned yet to a later pass — releasing it after packets that were actually sent later. Sorted per batch, but not globally. This was caught, not reasoned around: the very first live test showed retransmits going up with the feature on (197 → 1412), the opposite of the point of building it. Fixed by scanning and sorting the complete ready set before releasing anything, then chunking only the data-copy/delivery step afterward for bounded stack usage — the sort establishes the order once, chunking never gets to disturb it.

Actually built and run this time

Unlike the sessions below, this one wasn't just written and left uncompiled (see the closing note on this page) — it was built and tested end to end in WSL2: two network namespaces standing in for the router and the VPS, joined by two veth pairs shaped with tc netem to roughly 8ms and 34ms RTT — deliberately asymmetric, matching a real dual-ISP setup — each capped at 300mbit, with connections 8 per path (16 real sub-flows), the same shape as a real deployment.

single-flow iperf3, fresh daemon restart per condition
baseline (reorderwindow off)      94.8 Mbps    1146 retransmits
reorderwindow 25ms                81.1 Mbps     137 retransmits   (88% fewer)

Throughput moved in both directions across repeated runs — WSL2/netem itself turned out noisy under 16 concurrent shaped UDP sub-flows (individual sub-flows intermittently showing real loss with the feature off, one transient iperf3 control-connection reset, neither reproducible on retry) — but the retransmit-count drop was large and consistent in every clean run. That's the more direct signal of whether this mechanism is doing its job at all, since it's what the feature specifically targets; the noisier throughput numbers are believed to reflect the simulated environment, not the code, and real hardware should read cleaner on both counts.

One real-world mixup worth recording: resequencing only ever helps the receiving side of a given transfer — the sender doesn't reorder anything, it only stripes packets out. Set on the wrong end (the sender's own daemon) it silently does nothing for that direction. First real-hardware test enabled it on the wrong side for exactly this reason before the mistake was caught from the topology, not the numbers.

A flat window doesn't survive contact with a real long-haul path

The local WSL2 test above ran at 8-34ms RTT. Testing against a real VPS several hundred km away (~154ms and ~210ms RTT on the two paths, a ~28ms real one-way skew) exposed something the local test never could: the original flat-window design applies the same delay to every packet, including ones on the already-slow path that have nothing to wait for. At low RTT that flat tax is negligible next to the real transit time; at 150-200ms+ RTT it's a real, proportionally significant addition to every round trip — and a reorderwindow approaching the housekeeping loop's own ~100ms poll cadence introduced a second problem on top: release timing became inconsistent (some packets flushed quickly on real traffic, others waiting a full poll cycle), and that inconsistency in delay is exactly the kind of thing that confuses TCP's own RTO estimate.

flat window, ~154/210ms RTT paths, single flow
baseline (off)                    32-41 Mbps    406-1596 retransmits (noisy)
flat reorderwindow 20ms           24.9 Mbps        46 retransmits   (throughput down)
flat reorderwindow 50ms           35.5 Mbps      3074 retransmits   (worse than baseline)

50ms made retransmits worse than doing nothing at all — the opposite of the point, and the second time this feature has been caught regressing by a live test rather than by reasoning about the code (see the batch-scan bug above). The fix wasn't a bigger or smaller flat number -- it was recognizing the flat delay itself was the wrong shape: mud_path.reorder_hold now makes the delay adaptive per path, computed from real measured RTT (see the redesign described above), so a packet on the already-slowest path pays nothing at all, and only genuinely faster paths pay a delay proportional to their real speed advantage.

adaptive per-path hold, same ~154/210ms RTT paths, 60ms ceiling
baseline (off), 3 runs             23-32 Mbps      406-1596 retransmits
adaptive reorderwindow 60ms, 2 runs 33-39 Mbps    1100-1165 retransmits

No longer a regression -- trending toward a real ~35% throughput improvement across repeated runs, though single-flow TCP at this RTT stays inherently noisy in a simulated network even run to run at the same setting, so treat the direction as the finding, not the exact percentage. The idea for the adaptive redesign -- "why hold packets on the slow path at all, only the fast one" -- came from the user, not from re-reasoning about the code; the flat-window regression on its own hadn't obviously pointed at that particular fix.

root@joy:~# glorytun set dev gt0 reorderwindow 20ms
set dev gt0 kxtimeout 1h timetolerance 10m keepalive 25s reorderwindow 20ms

Same convention as keepalive/timetolerance/kxtimeout: 0 means "leave unchanged," not "disable" — once set, it can only be raised to a new value through this command, never reset back to 0 without restarting the daemon.

Held packets were released late on sparse traffic — found and fixed

Tested on two VMs with tc netem delaying the tunnel's sub-flows by UDP port to imitate two ISPs (fast group ≈ 4.4 ms round-trip, slow group ≈ 14.3 ms), using a small sequence-numbered UDP echo tool to count out-of-order packets and measure round-trip per packet. The feature does what it is for on a dense stream — but it added a large, unexpected delay to sparse traffic.

The bug

A buffered packet was only released when a worker next ran mud_reorder_flush(), and a worker only ran when a packet arrived or its 100 ms idle poll() timed out. Nothing woke a worker at the packet's own deadline. Dense traffic wakes workers constantly, so holds were accurate. A 20 pps flow instead got its held packet released one packet-gap late (or up to 100 ms late at 5 pps). The "release timing became inconsistent" seen on the long-haul test above was this same cause.

Made worse by noise

Two equal paths still differ by a few hundredths of a millisecond in smoothed RTT, so the "faster" one got a tiny non-zero reorder_hold and was buffered — and then hit the bug above. With no skew at all, round-trip went 4.7 ms → 36 ms.

The fix

1. The buffer tracks its earliest deadline (next_deadline); each worker's poll() timeout is now "time until that deadline" (rounded up to 1 ms), still capped at 100 ms. 2. A computed hold under MUD_REORDER_MIN_HOLD (500 µs) counts as measurement noise and becomes 0, so equal paths never enter the buffer.

Side find: a worker spun at 100% after a peer restarted — fixed

Found while measuring the CPU cost above (unrelated to resequencing). Once a path is confirmed live, the server moves it onto its own connected UDP socket. If that peer then disappears — client killed or restarted, source port changed — the kernel answers the next send with an ICMP "port unreachable", which sits on the socket as a pending error and makes poll() report POLLERR instantly, every time. The worker loop only handled POLLIN, so nothing ever consumed the error and the owning worker thread spun at ~100% of a core indefinitely (a fresh client did not clear it; a second dead client added a second spinning thread). The fix reads SO_ERROR on any socket that reports POLLERR, which clears it.

Sequence numbers: exact resequencing instead of a guess from RTT

The hold computed from RTT skew (above) is an estimate, refreshed only once per mud_update() tick (~100ms) and fuzzy by a few hundred microseconds even between two equal-speed paths. That is fine for a steady stream, where the next packet's arrival is itself the signal that lets the estimate self-correct. It is not fine for two cases: packets sent back-to-back in a burst, closer together than the estimate's own fuzz, whose relative order the estimate cannot resolve at all; and a lone packet on the fast path with nothing else in flight, which the flat estimate still delays by the full skew even though nothing needs waiting for. Both were confirmed by testing, not assumed -- see the two tables below.

Opt-in per direction, wire-compatible

reorderwindow being set now also tells the peer, in every control message, "stamp what you send me" (one new flag bit; the message only grows if this or the reply below applies, so a tunnel with the option off is byte-for-byte unchanged). A peer that understands the request stamps a 4-byte number onto each outgoing data packet -- inside the encrypted payload, so authenticated like the rest of it -- starting 2 seconds later (MUD_SEQ_LEAD) and announces that start time, in its own clock, in its own control messages, so both ends always agree which packets carry a number without needing an extra per-packet flag. An older build, or a peer with reorderwindow off, never gets asked and never stamps; its packets keep using the RTT-based hold above. Independent per direction, like the option itself.

Exact where a guess can't be

A numbered packet is released the moment every lower number has been delivered -- no estimate involved -- so an in-order packet, including the only packet of a sparse flow, is never delayed at all. A missing number is waited for up to the same RTT-derived hold plus a small margin, then given up on as lost, same trade-off as before, just applied to a real gap instead of every packet.

Two bugs live testing caught, same pattern as every other one on this page

The first version kept stamped packets in the same array as the RTT-hold ones and sorted the whole buffered set by sequence number on every flush -- correct, but O(n²) in however much was buffered, and a single TCP stream immediately built up a real backlog: CPU climbed to a full core within ~8 seconds and throughput collapsed by ~4x. Sequence numbers are already an array index, so the fix removes the sort entirely: stamped packets live in their own ring, seq % ring size, an O(1) write and read. That alone didn't fix it -- a second look-alike bug was hiding underneath: releasing packets also has to notice when a predecessor is genuinely missing, and the scan written to find that walked the entire ring every time it found nothing there, which is the common case (most packets need no holding at all). A cheap running count of what's actually buffered turned that into an O(1) check for the case that matters. Verified directly: a live debug trace during a TCP run showed the buffer staying at a stable 100-220 packets with small (1-10 slot) gaps throughout -- exactly the shape the design assumes -- confirming the fix, not just the CPU number improving.

TCP throughput is the one place sequence numbers measured worse than the RTT-hold method, and this is believed to be real, not a leftover bug: strict in-order delivery means a single delayed packet holds back everything sent after it until it either arrives or is given up on, then releases all of it in one burst rather than smoothly -- and that burst pattern, repeated continuously under sustained throughput, appears to disturb TCP's own ACK-clocked congestion control. Measured cleanly (a direct iperf3 run, no concurrent instrumentation -- an earlier measurement that polled CPU over a fresh SSH connection every second turned out to be contaminating the result itself and was discarded): off and the RTT-hold method reached 530-860Mbps with 43-3536 retransmits; sequence numbers reached 200-440Mbps with only 2-6 retransmits.

The bursty pattern, confirmed directly; a cheap fix for it, tried and disproven

A tcpdump capture of the tunnel's own decrypted traffic on gt0, during a live TCP upload, confirmed the theory directly rather than leaving it as a guess:

inter-packet gap, ms (mean / p99), and how often a run of packets is released all at once
                    data in (mean/p99)   ACKs out (mean/p99)   "burst-release" events
RTT-hold method       0.060 / 0.225 ms     0.087 / 0.417 ms     10
sequence numbers      0.281 / 5.021 ms     0.676 / 8.920 ms    191

19x more burst-release events, and the gaps between them 20x longer -- a real stop-and-go pattern, not a smooth stream, and it shows up in the ACKs the server sends back just as much as in the data it receives. The obvious cheap fix -- cap how many packets one mud_seq_flush() call releases at once, so a big backlog empties over several smaller calls instead of one -- was tried and made no measurable difference (4 runs, 194-268Mbps, the same range as without the cap). The reason became clear on reflection: under sustained throughput the worker loop calls mud_seq_flush() again immediately, with no real time elapsing between calls, so capping the count per call doesn't introduce any actual pacing, just more calls doing less work each.

A real playout-timer pacer was built and tested -- it fixed the burstiness and still didn't help

Built on the same idea as an audio/video jitter buffer: an EWMA of the recent gap between stamped packets arriving (same 1/8-weight smoothing mud_update_stat() already uses elsewhere), clamped to a 10-500µs range, used to schedule each release in a backlog a little after the previous one instead of all at once -- reusing the existing poll()-timeout plumbing (see mud_reorder_poll_timeout()) to actually wait for real time to pass between releases, rather than the cheap cap's mistake of just doing less work per call. Only ever engaged for a real backlog (more than one packet ready at once) -- a single ready packet, the sparse-flow case the very first fix in this section exists for, is still released immediately, untouched by any of this.

tcpdump capture on gt0, sequence numbers, without pacing -> with pacing

The pacing did exactly what it was built to do -- confirmed directly, not inferred from the throughput number alone -- and throughput still got worse, with retransmits climbing sharply in some runs. The mechanism: releasing a backlog immediately costs nothing beyond the hold already paid; pacing it instead adds more latency to every packet behind the first one, cumulatively -- the last packet in a 100-deep backlog at a 100µs pace now arrives 10ms later than it would have unpaced, on top of whatever hold and network delay it already had. TCP's retransmission timeout reacts to added latency and RTT variance more harshly than it does to a burst of otherwise-timely packets, so smoothing the delivery shape traded one problem for a worse one. Reverted; real evidence against the natural-seeming fix, which is itself a useful result.

The actual fix: don't stamp TCP at all

The question that unlocked this: TCP already carries its own sequence numbers, retransmission and (via SACK) a real reordering tolerance, tuned by decades of use across the whole Internet. This tunnel's own strict resequencing was never needed to give TCP ordering -- only to stop TCP's congestion control from misreading path-selection-induced reordering as loss, which the far cruder RTT-derived hold already did reasonably well (see the very first card at the top of this section). Layering exact ordering on top of TCP's own machinery was solving a problem TCP is already reasonably equipped to tolerate, at a cost (the bursty release pattern above) that TCP tolerates badly.

mud_is_tcp() reads a decrypted packet's inner IP header (version, then the protocol/next-header byte at the fixed offset that implies) to tell TCP apart from everything else, and both mud_encrypt() and the receive side now skip sequence-number treatment for TCP specifically -- a TCP packet still gets the RTT-derived hold if reorderwindow is set, just not the stricter, and for TCP counterproductive, sequence-number treatment. No wire-format change was needed: the classification reads bytes already present in the packet, computed identically on both ends, the same way mud_seq_active() already lets both sides agree on whether a packet is stamped without an extra flag. Wrong classification never affects correctness, only which of two already-safe paths a packet takes -- see the function's own comment.

§Group loss/RTT & losslimit

Found on a real production router, not a test VM: glorytun path showed one sub-flow of a visibly lossy ISP reporting 0% loss, seemingly at random, while its seven siblings on the same physical link all read 16-19%. It wasn't a display bug in the sense of showing a wrong number -- it was showing a real number that was no longer current.

Why one sub-flow can freeze

tx.loss/rx.loss only update when a tracking message from the peer, on that exact sub-flow, successfully arrives with fresh counters (mud_recv_msg()). On a genuinely lossy link, a sub-flow's own status reports are subject to the same loss being measured -- confirmed live with a 25-second continuous capture: one sub-flow's numbers (tx-loss 61.18, rx-loss 0.00, even rx-loss-live 12.16) never moved once, while its siblings updated every second. Not covered by the existing idle-ageing safety net either -- that only fires when no real data has moved, and this sub-flow's real data was flowing fine; only its own status reports kept getting lost.

The fix: pool sub-flows of one physical link

Capacity already gets this treatment -- select_weight has long been the average tx.rate across a group's RUNNING members, not each sub-flow's own. Loss and RTT now get the same treatment: a new struct mud_group, one per physical link (same identity rule as mud_path_same_group()), with its own rolling loss tracker fed by any member's successful report. A stuck sub-flow simply contributes nothing to that tick, rather than contributing a wrong number -- with 8 sub-flows each beating roughly every 100ms, the group as a whole goes quiet only if every one of them does at once.

losslimit/MUD_LOSSY now group-wide too

Requested directly: a whole physical link should degrade and recover as one unit, not sub-flow by sub-flow. mud_path_update()'s losslimit check now reads the group's pooled figure, so every sub-flow of a link crosses into MUD_LOSSY (select_weight = 0, meaning zero traffic) together, and recovers together once the pooled rolling average -- the same 60-second window as before, just pooled -- drops back under the threshold. Per-sub-flow tx-loss/rx-loss are untouched and still shown, for diagnosing which specific sub-flow's reports are the ones going missing (as above) -- they just no longer drive the degrade decision on their own.

Two bugs, both caught only by running it, same as every other feature on this page

Display grouping didn't match the real grouping. glorytun path's own header-line grouping compared remote port as well as address -- fine from the active side (every sub-flow shares one fixed remote port), but on the passive side, where each auto-discovered sub-flow has a distinct remote port by definition, it silently split one physical link into eight separate one-line "groups". mud_path_same_group() inside mud.c never compared port for exactly this reason; the CLI's own copy of that rule (gt_path_same_group() in src/path.c) had drifted from it. Fixed by dropping the port comparison there too -- confirmed on the VMs' passive side, which now prints one header for all 8 sub-flows instead of 8.

The group's own idle handling fought its own live feed. The first version also aged the group's rolling tracker once per tick whenever every member's traffic_idle was true, mirroring what individual paths already do. Missed: traffic_idle deliberately tracks only real data, not beat/tracking traffic -- and with multiple sockets, beats never back off, so a tunnel exchanging only beats (the common case between bursts of real traffic) has every member "idle" by that definition almost continuously. The per-tick ageing call fired on nearly every ~100ms tick, resetting the tracker's in-progress bucket before the event-driven feed's own sample ever closed into it. Caught live: after clearing an injected 20% loss, the published figure sat frozen for 45 seconds, then jumped straight to 0% in one step, instead of the smooth decline a 60-sample rolling window should show. Fixed by removing that call entirely -- a group's tracker never needs an idle fallback the way a single path's does, precisely because it always has multiple sockets feeding it. Retested the same way: loss climbed to a near-exact 20.00% under injected loss, then decayed smoothly (20.00 → 15.29 → 10.20 → 4.31 → 0.00) over the following minute once the loss was cleared, crossing back to running right as it passed under the 5% threshold.

Also confirmed a single very badly behaved sub-flow can't drag the group down: one sub-flow 100%-blocked (in both directions) alongside seven healthy ones at ~2% real loss still read a group figure close to 2%, not skewed toward either the blocked sub-flow's frozen 0% or a false 100% -- a silent member contributes nothing to the pool, in either direction, exactly as intended.

The individual sub-flow numbers themselves, not just the group figure they feed

The group figure above fixes the decision -- losslimit/MUD_LOSSY no longer depends on any one sub-flow's luck. It deliberately left each sub-flow's own displayed tx-loss/rx-loss untouched, still subject to the original problem: they only update when a message from the peer, on that exact sub-flow, successfully arrives. Asked directly afterward: should a sub-flow's own number also stop freezing, independent of anything group-level? Yes -- a value stuck on the screen for 40-50 seconds is itself the complaint, whether or not a decision depends on it.

Fixed the same way individual paths already handle going fully idle (mud_path_track()'s existing idle-ageing call), extended to a second, independent trigger: two new per-path timestamps (msg.tx_seen, and the already-existing msg.rxloss.time) record, in this side's own clock, the last time this sub-flow's tx or rx loss had anything fresh to compute from. Once more than MUD_MSG_SENT_MAX beats (the same threshold mud_path_update() already uses to call a path unresponsive) have passed since one of them, that specific tracker -- tx and rx independently, since one can be stuck while the other isn't -- gets the same "age by one empty bucket per elapsed second" treatment idle paths already get, instead of sitting frozen indefinitely. Real data can keep flowing on the path the whole time; this fires purely off whether this sub-flow's own status reports specifically have gone quiet, which traffic_idle (data only, by design) doesn't track.

Deliberately gated on a real elapsed-time condition rather than firing on every tick -- the group-level attempt above got this wrong by trying an unconditional per-tick call and it fought its own live feed. "Stuck for N beats" avoids that by construction: while genuinely stuck, the event-driven feed isn't succeeding anyway, so there's nothing for the two to collide over; the moment a real message gets through, its own timestamp update makes the very next tick's stuck-check pass again.

glorytun bind [dev NAME] [addr LOCAL_IP [PORT]] keyfile FILE [persist] [chacha] [qlen N] [workers N] [cpus LIST] workers, cpus are new

Starts the tunnel: creates/attaches the TUN device (on Linux, attaches to a pre-existing device of that name if one exists), opens the UDP socket, and runs the event loop until stopped. Runs in the foreground.

persist keeps the Linux TUN device alive when the process exits — useful with via-bound paths so netifd doesn't flap the interface across a crash/respawn. chacha forces the ChaCha20-Poly1305 fallback instead of negotiating AEGIS-256. qlen sets the TUN device's tx queue length (txqueuelen) once at startup — Linux defaults TUN/TAP interfaces to 500 (vs. 1000 for a typical Ethernet interface); raise it if real bulk traffic through the tunnel could burst past that. Unlike mtu on path up, this is a one-time value applied once when the interface is created, not something that needs to keep tracking path config afterward.

workers sets exactly how many worker threads to run, overriding the automatic default of usable cores − 1 (usable = the cores this process is allowed to run on, so a cpus limit, taskset or systemd CPUAffinity= is respected). workers 8 gives exactly 8 workers, not 7 — the "minus one" applies only to the automatic default. A separate housekeeping thread (the original main thread: the ~100 ms path tick, the control socket, network-change events) always runs in addition, using well under 1% of a core. The value is capped at 4 × usable cores, at most 64, so asking for more workers than cores is allowed. Historical note: when every worker shared one poll wakeup on the TUN device, more workers than real connections N sub-flows measurably reduced throughput (numbers in Scaling for many-core hardware). Workers now each read their own TUN queue, and on a 3-core limit 8 workers ran as fast as 3 within run-to-run noise (Core placement & interrupts). What still matters is that your path count divides evenly by the worker count: 16 paths over 3 workers is 6/5/5, so one worker carries about 20% more; over 8 workers it is 2 each.

cpus confines the whole process — every worker and the housekeeping thread — to the listed cores, e.g. cpus 0-2 or cpus 0,2, and leaves placement inside that set to the scheduler (it does not pin one worker per core). Its purpose is to keep glorytun off the core that services the network card's interrupts, which otherwise ends up pegged at ~100% while the others idle (see Core placement & interrupts). A core that doesn't exist or isn't available is an error and glorytun refuses to start (exit 255, no tunnel device created); Linux only. Given without workers, the default is one worker per listed core. Equivalent to taskset -c or CPUAffinity=, but part of the command line and it works where taskset isn't installed.

Two problems found from working through what the design implies in practice, both requested explicitly after real testing, not speculative hardening.

Sub-flows were being selected by measured rate, not evenly. mud_select_path() weights by tx.rate — correct for bonding two different-capacity physical links, wrong for sub-flows of one link, which have no real capacity difference from each other. Left alone: a rich-get-richer trap, since whichever sub-flow(s) pull ahead early get selected more (selection weight is measured rate), keeping their rate estimate growing while idle siblings never get real traffic to prove themselves against. New struct mud_path.select_weight (mud.h), recomputed every mud_update() tick: a new mud_path_same_group() helper (next to mud_cmp_addr()/mud_cmp_port()) identifies which MUD_RUNNING paths share one physical link — same local_ifindex (or local address for legacy/passive paths) and same remote address, deliberately excluding remote port, since sub-flows vary by local port on the active side but by remote port on the passive side, which never opens extra sockets. src/bind.c

A rare (~1% per sub-flow) stuck-sub-flow bug, found stress-testing large connections N counts on the upgraded hardware: bringing up a big fresh batch of sub-flows at once could leave one of them permanently degraded — rtt stuck at 0, never self-healing despite ongoing beat retries. Root-caused over several rounds of instrumentation on paired VMs, not guessed at:

  1. First hypothesis — every sub-flow's first handshake-carrying packet racing for the initial ECDH key exchange before any session key exists — led to bringing up sub-flow 0 alone first, confirming its key exchange completed (polling rtt.setup), then releasing the rest together. A first version of this fix introduced a new bug in the process: blocking the housekeeping thread in a plain usleep() wait loop also silently stalled mud_update(), which the wait was itself depending on to make progress — caught before shipping, fixed by calling mud_update() inside the wait loop instead of just sleeping.
  2. That fix measurably helped but didn't eliminate the problem. Simultaneous tcpdump on both VMs, and instrumented tracing through mud_recv_finish()/mud_worker_loop()'s poll() loop, proved the real remaining cause: a stuck sub-flow's replies genuinely arrive at the receiving machine's network interface — visible on the wire, correctly addressed — but the kernel never delivers them into that specific freshly-bind()'d socket's receive queue, for that socket's entire remaining lifetime. Not a glorytun logic bug; a kernel/virtualized-NIC-level UDP delivery anomaly triggered by binding on the order of 100 new sockets in one uninterrupted burst.

Mitigated, not eliminated, by growing the socket pool in small chunks (8 at a time, 20ms apart) instead of one bulk mud_set_sock_count() call for a brand-new connections N > 8 group — repeated fresh-restart connections 100 trials went from a real chance of losing a sub-flow on nearly every attempt down to roughly 1 in 8–10, and connections 32 or fewer showed zero failures across 45 trials (1,400+ sockets) with chunking in place.

mud/mud.c

Server-side sub-flows get a dedicated socket, assigned in order. The passive side opens workers × 16 SO_REUSEPORT sockets on one port, and the kernel's hash of the remote address picks which one a new sub-flow lands on. A worker owns sockets by index % worker_count, so which worker served a flow was decided by hash luck. Measured on 8 workers and 16 real flows: one worker got none (0.03% CPU) and another got six (83%), confirmed by mapping each flow's socket index mod 8 on the server, with CPU pinning ruled out as the cause (below). With fewer workers per flow the chance is smaller (4 workers over 16 flows came out 4/4/4/4) but never zero.

Fix: mud_path_promote() opens a fresh socket on the same local port, connect()ed to that exact remote, appended at the next sock_count index. Linux delivers to an exact-match connected socket before the reuseport hash, and appending in order makes index % worker_count a strict round-robin — the guarantee the client side already had for connections N. Result on 32-core VMs, 8 workers, 16 streams, 2.3 Gbit/s: two flows per worker, workers at 53–55% each.

mud/mud.c
mud/mud.h

Only promote a path that has proved it is alive. Promoting on the first packet leaked file descriptors: mud->sock[] is append-only by design (a worker reads a slot without a lock, so closing or reusing one would be a use-after-close race), and the 5-minute idle reap clears the path but never its socket. A killed peer's kernel can keep flushing already-queued packets for a long time (a steady trickle spanning about 20 s was captured), each one decrypting fine under the pre-shared key, so every such ghost cost one fd permanently, bounded only by MUD_PATH_MAX.

A first fix — wait a few beat intervals before promoting — was measured not to work: a fresh path always passes the waiting check on its first tick, and a trickle keeps refreshing it. The fix that holds: new fields created and confirmed_live; mud_recv_msg() sets confirmed_live only when a reply's echoed timestamp is ≥ created. mud_now() is wall-clock based (base_time + CLOCK_MONOTONIC) and keeps advancing across a process restart, and a dead process cannot echo a timestamp from after it died, however long its queue keeps draining. Promotion (from mud_path_update(), the housekeeping tick) requires it.

Deterministic test: a firewall rule on the client dropped the server's replies. The server's path stayed on its shared socket (index 69), degraded, rtt 0.000, for as long as the rule stood. With the rule removed, the next completed round trip promoted it to index 144, running, rtt 0.347 ms. Real flows are promoted within one round trip.

Why one core gets pegged

The kernel does the receive-side work for the network card on a small number of cores, and a glorytun worker sharing one of them can't get away from it. Each virtual NIC on the test VMs has a single receive queue with all its interrupts on one core (about 35% softirq on the server's core 0, 29% on the client's core 3); the router is the same story with USB adapters. That core is busy with work glorytun doesn't control, and any worker on it becomes the bottleneck. Two further measurements: turning on receive packet steering (RPS, rps_cpus) flattened the client (per-core busy from 24–87% to 43–71%) but barely helped the server, whose interrupt core still takes the interrupt itself; and the client's leftover 77% vs 68% worker skew was purely arithmetic — 16 paths over 3 workers is 6/5/5, and 77/68 is that same ratio.

Keeping glorytun off the interrupt core — a boot script

Kept out of the source tree (it is system configuration, not glorytun). It moves a named interface's interrupts to a core you choose; run it at boot, then give glorytun the other cores with cpus. Plain POSIX sh, so the same file works on OpenWrt (busybox ash) and Debian/Ubuntu. It finds the interrupts three ways: PCI/virtio MSI-X vectors, the xHCI controller behind a USB NIC, and interrupts named after the interface. Tested on a virtual NIC (the interrupts moved and only the target core's counter grew under traffic) and against a replica of the Pi's real directory layout (only eth2's interrupt moves, eth1's and the built-in port's do not). Not run on the real router — see below.

nic-irq-affinity.sh
#!/bin/sh
# nic-irq-affinity.sh -- put a network interface's interrupts on the CPU core(s)
# you choose, so glorytun can be kept on the OTHER cores. Plain POSIX sh.
#   nic-irq-affinity.sh start     move the interrupts (run this at boot)
#   nic-irq-affinity.sh status    show where they are now and whether they fire
NICS="${NICS:-eth2}"          # interface(s) whose interrupts to move
IRQ_CPUS="${IRQ_CPUS:-3}"     # target core(s). Several ("2 3") = spread round-robin
WAIT="${WAIT:-60}"            # seconds to wait for the interface to appear at boot
SYS="${SYS:-/sys}"            # only overridden by tests
PROC="${PROC:-/proc}"

log() { echo "nic-irq-affinity: $*"; logger -t nic-irq-affinity "$*" 2>/dev/null; }

# Print the IRQ numbers that serve interface $1, one per line.
irqs_of() {
    nic=$1
    dev=$(readlink -f "$SYS/class/net/$nic/device" 2>/dev/null) || return 0

    # PCI and virtio NICs: MSI-X vectors (virtio's PCI device is a parent of the net device)
    d=$dev
    for _ in 1 2 3 4; do
        if [ -d "$d/msi_irqs" ]; then ls "$d/msi_irqs"; break; fi
        d=$(dirname "$d")
    done

    # USB NICs (e.g. Raspberry Pi): the interrupt belongs to the USB host controller
    # (xhci-hcd.N), and /proc/interrupts names it after that controller's first bus.
    case $dev in
    */xhci-hcd.*/usb[0-9]*)
        ctrl=${dev%%/usb[0-9]*}
        for bus in $(ls "$ctrl" 2>/dev/null | grep '^usb[0-9]'); do
            grep "xhci-hcd:$bus\$" "$PROC/interrupts" | cut -d: -f1 | tr -d ' '
        done ;;
    esac

    # Drivers that name their interrupts after the interface (eth0-TxRx-0, ens18-input.0, ...)
    grep -w "$nic" "$PROC/interrupts" 2>/dev/null | cut -d: -f1 | tr -d ' '
}

all_irqs() {
    for nic in $NICS; do irqs_of "$nic"; done | grep '^[0-9][0-9]*$' | sort -un
}

wait_for_nics() {
    t=0
    for nic in $NICS; do
        while [ ! -e "$SYS/class/net/$nic" ] && [ "$t" -lt "$WAIT" ]; do sleep 1; t=$((t + 1)); done
        [ -e "$SYS/class/net/$nic" ] || log "interface $nic did not appear within ${WAIT}s"
    done
}

do_start() {
    wait_for_nics
    irqs=$(all_irqs)
    if [ -z "$irqs" ]; then
        log "found no interrupts for: $NICS (nothing changed)"
        return 1
    fi
    if command -v pidof >/dev/null 2>&1 && pidof irqbalance >/dev/null 2>&1; then
        log "WARNING: irqbalance is running and may move these interrupts back"
    fi
    set -- $IRQ_CPUS
    n=$#
    i=0
    for irq in $irqs; do
        eval "cpu=\${$((i % n + 1))}"
        i=$((i + 1))
        if echo "$cpu" > "$PROC/irq/$irq/smp_affinity_list" 2>/dev/null; then
            now=$(cat "$PROC/irq/$irq/smp_affinity_list" 2>/dev/null)
            if [ "$now" = "$cpu" ]; then
                log "irq $irq -> core $cpu"
            else
                log "irq $irq: asked for core $cpu, kernel now reports '$now'"
            fi
        else
            log "irq $irq: the kernel refused to move it (this hardware may not allow it); left as is"
        fi
    done
}

do_status() {
    echo "core columns below are per-core interrupt counts; the growing column is the one in use"
    head -1 "$PROC/interrupts"
    for irq in $(all_irqs); do
        grep "^ *$irq:" "$PROC/interrupts"
        echo "    ^ irq $irq allowed cores: $(cat "$PROC/irq/$irq/smp_affinity_list" 2>/dev/null)"
    done
}

case "${1:-start}" in
    start)  do_start ;;
    status) do_status ;;
    *)      echo "usage: $0 [start|status]"; exit 2 ;;
esac

IRQ_CPUS is the core (or cores) to move the interrupts onto. One number puts every interrupt of the interface there; several numbers hand a multi-queue card's interrupts out in turn, round-robin. Use a single core unless one interrupt core becomes the ceiling.

§What changed — a later session, a tx-loss underflow at path promotion

Reported from production: one sub-flow's loss dominating the whole group figure. Tried an averaging-based redesign of the group pool first, on request, then reverted it whole -- on request -- back to the existing byte-count pooling above once it was live on the VMs. What survived the round trip: a real, separate, pre-existing bug found while re-verifying the reverted code matched production exactly, root-caused, fixed, and reproduced on demand.
mud/mud.c

An unchecked packet-count echo let tx-loss underflow to ~100% for up to a minute, with no real problem on the wire. mud_recv_msg()'s guard before computing the tx-loss delta checked tx_time, tx_bytes, rx_time and rx_bytes for strictly increasing, but never tx_total -- the packet count actually subtracted (tx_total - path->msg.tx.total) to get the "sent" side of the ratio fed to mud_update_rl(). tx_total arrives by echo (msg->fw.total, the peer's own re-transmission of a value this side told it), one extra round trip removed from tx_bytes -- and control messages ride the same per-packet-striped sockets as data (Packet resequencing), so they're exactly as subject to arriving out of send order. A message whose echoed tx_total was momentarily behind what had already been recorded, while every other field still looked forward-moving, used to pass this guard anyway; every field here is unsigned, so the subtraction doesn't go negative, it wraps to a number near UINT64_MAX. Fed into mud_update_rl() as this sub-flow's "sent" count against a real, small "received" count, that reads as ~100% loss for one window -- sitting in the 60-sample rolling tracker until it fully ages out, up to a minute later. The rx-loss side of the same function already guarded both of its own two fields (peer_tx_total and peer_tx_bytes) for exactly this reason; the tx side only ever checked one of its two. Fix: add the same tx_total > path->msg.tx.total (and, symmetrically, rx_total > path->msg.rx.total) terms to the existing guard.

Why the first attempt to catch it live found nothing

Reasoned the trigger was reordering under jitter, so the first test ran 4 minutes of dense UDP traffic over 8 skewed, jittered sub-flows (2–7 ms path skew, 3 ms jitter each way) -- confirmed 57–71% of real data packets genuinely arrived out of order, but zero of the debug-instrumented rejections fired on either end. The miss: mud_send_msg() sends each sub-flow's own control traffic on that exact sub-flow's own socket, never striped across sub-flows the way data is, so control-message reordering can't come from data-level per-packet path selection at all. What it can come from: mud_path_promote() -- called once, right at bring-up, when a passive sub-flow first proves live (confirmed_live) -- moves that sub-flow from a shared, hashed SO_REUSEPORT socket onto a brand-new dedicated one, which a different worker thread can own. A message already queued on the old socket when this happens, and a newer message that's already arrived on the new socket, both resolve to the same struct mud_path (lookup is by remote address, not socket) but can be processed by two different worker threads in either order -- a promotion-time race, not a steady-state one, and therefore invisible to a test that only started measuring after the connection had already settled.

Reproduced directly once the test targeted bring-up instead

25 fresh tear-down/bring-up cycles, 16 sub-flows each, debug logs kept across the whole run instead of truncated after settling (the first version of this test discarded exactly the window it needed). Caught 5 real would-have-corrupted messages -- 4 on the client, all on the same newly-promoted socket, each showing tx_total sitting behind a baseline that had already moved on; 1 on the server, an exact non-increasing duplicate. All 5 landed on socket indices past the reserved passive pool, i.e. on sockets promotion itself had just created, confirming the mechanism precisely. With the fix in place, these are rejected -- the update for that message is simply skipped, not replaced with a wrong one -- rather than corrupting the rolling window.

Nothing else regressed

A 4-minute steady-state soak straight after a fresh bring-up (same jitter/reordering setup as the first test, now correctly capturing the promotion window too): zero further rejections once bring-up settled, as expected -- promotion is one-time per sub-flow. Group RTT changed on every single poll (proof the group tick itself was never stuck), group and per-sub-flow tx-loss/rx-loss stayed non-null and sane throughout, and tx-loss-live/rx-loss-live correctly read null only for sub-flows carrying no real data that particular second (src/path.c's existing traffic_idle gate, unrelated to this fix) while showing genuinely varying values on the one sub-flow that did carry data. Real injected loss (netem, 30% on one targeted sub-flow) still rises and decays exactly as designed on the fixed build -- climbed to tx-loss 14.12 on the targeted sub-flow under load, group pooled it proportionally rather than skewing toward it, and both decayed smoothly over the following rolling-window minute once the loss was removed. One single-poll reading mid-test looked like a fresh spike (group tx-loss 45.49% shortly after clearing loss) and was re-investigated on suspicion it might be a second bug; a controlled repeat with full per-sub-flow visibility and denser polling showed the same figure is simply the known rolling-window residue from the just-cleared real loss (see Group loss/RTT above) -- elevated, then visibly decaying every subsequent poll, never stuck.

Resequencing was different: built and tested end to end, but only in a WSL2-simulated network (see that section) — real hardware, real ISPs, no substitute.
