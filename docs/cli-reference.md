# CLI reference

Glorytun is a single binary with eight commands:

```text
glorytun list
glorytun show
glorytun bench
glorytun bind
glorytun set
glorytun keygen
glorytun path
glorytun version
```

Arguments are bare words, not GNU-style options. For example, write `glorytun
show dev gt0`, not `glorytun show --dev gt0`. Nested address and path groups
also support compact positional forms; `bind 0.0.0.0 5000` is equivalent to
`bind from addr 0.0.0.0 port 5000`. Running `glorytun help` or a command-specific
help invocation prints generated contextual help.

## `keygen`

```sh
glorytun keygen
```

Prints a random 32-byte secret as 64 hexadecimal characters. Both peers must
use the same key. Store it with permissions appropriate for a secret, such as
mode `0600`.

## `bind`

Starts a foreground tunnel process:

```text
glorytun bind keyfile FILE [dev NAME]
  [from addr LOCAL_IP port LOCAL_PORT]
  [to addr REMOTE_IP port REMOTE_PORT]
  [persist] [chacha]
```

Options:

* `keyfile FILE` is required. Its first 64 bytes must be the hexadecimal key
  generated by `keygen`.
* `dev NAME` requests a specific TUN device. Otherwise, Glorytun tries device
  numbers 0 through 31.
* `from ...` selects the local UDP bind address. The default is
  `0.0.0.0:5000`.
* `to ...` selects the initial remote endpoint. Its default is also
  `0.0.0.0:5000`; a listening peer can learn usable path information through
  the transport protocol.
* `persist` leaves the Linux TUN device in place when the process exits.
* `chacha` forces ChaCha20-Poly1305. Without it, Glorytun requests AEGIS-256
  and automatically falls back to ChaCha20-Poly1305 when the platform lacks
  the required AES support.

The command:

1. initializes libsodium and reads the shared key;
2. creates the `mud` UDP transport and TUN interface;
3. creates a local Unix datagram control socket named after the TUN device;
4. forwards validated IPv4/IPv6 packets between TUN and `mud`; and
5. applies newly discovered path MTUs to the TUN interface.

It logs the selected device and PID to standard error and stays in the
foreground.

The equivalent compact endpoint syntax is:

```text
glorytun bind LOCAL_IP [LOCAL_PORT]
  [to REMOTE_IP [REMOTE_PORT]]
  keyfile FILE [dev NAME] [persist] [chacha]
```

## `list`

```sh
glorytun list
```

Prints the device name for each tunnel discoverable in the current effective
user's control directory.

## `show`

Show general status:

```sh
glorytun show [dev NAME]
```

The output includes device name, local and remote UDP endpoints, process ID,
discovered MTU, and selected cipher.

Show protocol error counters:

```sh
glorytun show [dev NAME] errors
```

This reports non-zero decrypt, clock-sync, and key-exchange errors, including
the last associated source address.

The `dev` selector can be omitted when exactly one tunnel is active. It is
required when multiple tunnels are present.

## `set`

Changes transport-wide runtime properties:

```text
glorytun set [dev NAME]
  [kxtimeout DURATION]
  [timetolerance DURATION]
  [keepalive DURATION]
  [reorderwindow DURATION]
```

Durations accept the suffixes understood by the bundled argument parser, such
as `ms`, `s`, `m`, `h`, and `d`. The resulting configuration is printed after
a successful update.

* `kxtimeout` controls key-rotation timing.
* `timetolerance` controls the accepted clock offset between peers.
* `keepalive` controls idle keepalive timing.
* `reorderwindow` controls the packet-resequencing buffer described below.
  Off (`0`) by default; like the other durations here, it can only be raised
  to a new nonzero value through this command, not explicitly reset back to
  `0` once enabled.

Example:

```sh
glorytun set dev gt0 kxtimeout 1h timetolerance 10m keepalive 10s
```

Use relaxed clock tolerance only as a temporary diagnostic measure; fixing
time synchronization is preferable.

### Packet resequencing

Multipath striping schedules per packet, not per flow (see `connections`
below), so a single ordered-delivery flow -- almost always TCP -- crossing
several physical paths at once will routinely see its packets arrive out of
order, since paths differ in latency. TCP reads that as loss and throttles
itself even though nothing was actually dropped, which is why a lone flow
measures well below a multipath tunnel's combined throughput while several
concurrent flows, run in parallel, add up to close to it.

```sh
glorytun set dev gt0 reorderwindow 20ms
```

Once set, decrypted packets are briefly buffered tunnel-wide (across every
path) and released to the TUN device in send order rather than arrival
order, so a single flow no longer sees the reordering. This adds up to
`reorderwindow`'s own duration of latency to every packet on the tunnel --
not just the flow benefiting from it -- so treat it as a throughput/latency
trade-off to size deliberately, not a setting to maximize. It defaults to
off; existing deployments see no behavior change unless this is configured.

## `path`

Paths are the local-interface or local-address/remote-endpoint combinations
available to a tunnel. A selector may include either `via INTERFACE` or `addr
LOCAL_IP`:

```text
dev NAME [via INTERFACE | addr LOCAL_IP]
  to addr REMOTE_IP port REMOTE_PORT
```

Omitted selectors act as wildcards. If a remote address is supplied without a
port, the tunnel's configured remote port is used. `via` is Linux-specific and
cannot be combined with `addr` in one request.

An interface-managed path keeps its configured interface name when the link
goes down, loses its address, or is deleted. Glorytun monitors link and address
changes, resolves the current interface index and a suitable address, and
automatically returns the path to probing when the interface becomes usable
again. The remote endpoint selects whether an IPv4 or IPv6 interface address
is required.

### Show paths

```sh
glorytun path [SELECTOR]
glorytun path [SELECTOR] watch
```

There is one view, not several -- a `rtt`/`stat` distinction existed at one
point but was removed once the default view grew live `tx`/`rx` throughput
figures that made the specialized views largely redundant with it. Output is
grouped by physical path, not a flat table: one header line per path
(interface, index, local and remote address), followed by one indented line
per sub-flow (`connections N`; a path with no sub-flows configured just
renders as a group of one). Each sub-flow line reports its status, live
observed `tx`/`rx` throughput in Mbps (a real client-side-computed rate, not
the AIMD-allowed budget), round-trip time, transmit/receive loss, the fixed
MTU in effect, and the observed public endpoint. Loss is shown as two
figures per direction: a stable 60-second figure (drives the state below)
and a live figure refreshed roughly every second, printing `null` instead of
a bare `0` while the sub-flow has carried no recent traffic. Live `tx`/`rx`
throughput requires two samples a second apart to compute, so it only shows
real numbers under `watch` -- a one-shot query has nothing prior to diff
against and shows `-`.

`watch` refreshes the view in place once a second until interrupted
(Ctrl+C), instead of printing once and exiting.

Path states reported by the transport include `deleting`, `probing`,
`degraded`, `lossy`, `waiting`, `ready`, and `running`.
Interface-managed paths also report `interface-down`, `waiting-address`, and
administrative `down` states.

There is no MTU discovery or probing: each path sends at a single fixed wire
size, set with `mtu` (see below) and never adjusted based on send failures or
silently black-holed traffic.

### Change a path

```text
glorytun path up|down [LOCAL_IP] [SELECTOR]
  [beat DURATION]
  [pref NUMBER]
  [connections NUMBER]
  [losslimit PERCENT%]
  [rttlimit DURATION]
  [mtu SIZE]
  [rate [fixed|auto] [tx RATE] [rx RATE]]
```

Configure a path by durable Linux interface name:

```sh
glorytun path up via wwan0 rate tx 10mbit rx 50mbit
glorytun path down via wwan0
```

The current address is selected automatically. The desired rates, preference,
beat interval, loss limit, and administrative state survive address and
interface-index changes.

The local IP immediately after `up` or `down` is the compact form of `addr
LOCAL_IP`. For example, the bundled setup script uses this style:

```sh
glorytun path up 192.0.2.20 dev gt0 rate tx 12500000 rx 12500000
```

Important units and behavior:

* `tx` and `rx` are stored as bytes per second. Status/configuration output
  renders them as bit rates.
* Size suffixes are accepted by the argument parser.
* `pref` ranges from 0 to 127; use it to prefer one path over another.
* `losslimit` ranges from 0% to 100% and allows lossy paths to be disabled.
* `rttlimit` takes a duration (e.g. `rttlimit 250ms`); once measured RTT
  exceeds it the path is marked `late` and stopped, the same way `losslimit`
  marks a path `lossy`. It re-enables itself automatically once RTT drops
  back under the limit. Unset (or `0`) disables the check, which is the
  default.
* `mtu` sets the fixed wire size this path sends at. Unset (`0`, the
  default) uses the library default, `1400`. It's also sent to the peer in
  every beat message: a path with no explicit local `mtu` of its own instead
  adopts whatever its peer last advertised, kept live-updated rather than
  negotiated once -- so setting it on one end alone is usually enough.
  Rejected above `65535` at the command line; the transport enforces the
  same hard ceiling internally regardless, since its fixed packet buffers
  are sized to it. A newly configured value takes effect immediately.
* `fixed` uses the configured limits. `auto` enables experimental dynamic rate
  detection.
* `connections` splits this path into that many independent parallel UDP
  sub-flows (distinct local ports), load-balanced by the same weighted
  scheduler that already bonds separate physical paths -- useful for
  aggregating throughput past a single flow's bandwidth-delay-product ceiling
  on long/high-RTT links, similar to running several parallel TCP streams.
  Requires `via INTERFACE` (not supported for legacy `addr`-only paths).
  Default `1`; `0`/unset leaves an existing path's sub-flow count unchanged.
  The peer needs no configuration -- each sub-flow is a normal UDP flow from a
  distinct source port, and the passive side already auto-creates one path
  per distinct source port it observes.

When changing one path in a multipath tunnel, provide enough of the selector to
identify it unambiguously.

## `bench`

Benchmark AEGIS-256:

```sh
glorytun bench
```

Benchmark the ChaCha20-Poly1305 fallback:

```sh
glorytun bench fallback
```

The benchmark tests payload sizes from 20 through 1450 bytes and reports
minimum, mean, and maximum throughput. It is a crypto microbenchmark -- it
never touches the network, TUN device, or the worker pool used at runtime.

Benchmark aggregate multi-core throughput:

```sh
glorytun bench multicore
glorytun bench multicore fallback
```

For each payload size, reports two figures using the same thread count the
running transport's worker pool would use on this machine: an independent
*ceiling* (every thread encrypting with no shared state -- the theoretical
maximum) and the transport's actual *pool* pattern (threads sharing one
mutex-guarded job queue, matching the real implementation). The percentage
gap between them is the pool's own coordination overhead, measured directly.

## `version`

```sh
glorytun version
```

Prints the Glorytun version and the linked libsodium ABI version on separate
lines. The Glorytun version is a fixed literal in the binary, not derived from
git metadata or a `VERSION` file, so it reads correctly even when built from a
source tarball with neither present (for example, most downstream packaging).

## Control-socket discovery

Management commands communicate with `bind` over Unix datagram sockets. The
first writable parent directory in this order is selected:

```text
/run/user/<euid>/glorytun
/run/glorytun.<euid>
/var/run/glorytun.<euid>
/tmp/glorytun.<euid>
```

The selected directory is created with mode `0700`, and the server socket is
named after the TUN device. Commands must run as the same effective user to
discover it. The binary control messages are an internal, same-build protocol;
they are not a stable external API.

## Signals

* `SIGINT`, `SIGQUIT`, and `SIGTERM` stop the foreground process.
* `SIGHUP` stops it and requests a persistent TUN device before exit.
* `SIGPIPE`, `SIGUSR1`, and `SIGUSR2` are ignored.

## systemd and networkd integration

When Meson detects systemd, installation includes:

* `glorytun@.service`, an instance service reading
  `/etc/glorytun/<instance>/env`;
* `glorytun-run`, which translates environment values into `bind` arguments;
* `glorytun-setup`, an interactive configuration generator; and
* two systemd-networkd profiles for `gt-*` server and `gtc-*` client devices.

After installation, an administrator can run:

```sh
sudo glorytun-setup
sudo systemctl enable --now glorytun@INSTANCE
```

The generated key is stored at `/etc/glorytun/INSTANCE/key`, configuration at
`/etc/glorytun/INSTANCE/env`, and optional post-start routing in `post.sh`.
Review all generated networking and rate-limit values before production use.
